# mytasks — набор служебных скриптов

Коллекция bash/Python-скриптов для автоматизации повседневных задач.

## Быстрый старт на новой машине

```sh
git clone git@github.com:Eremiteb/mytasks.git ~/esimych-docs/mytasks
~/esimych-docs/mytasks/check_mytasks.sh --dry-run   # сначала план
~/esimych-docs/mytasks/check_mytasks.sh             # вопросы в окне, создание
```

[`check_mytasks.sh`](#check_mytaskssh) определяет семейство ОС (Arch, Debian,
Red Hat и др.), обязательно обновляет систему, прописывает себя в автозагрузку,
записывает каталог mytasks (тот,
откуда запущен) в `conf/check_mytasks.conf`, проводит мастер конфигов, ставит
зависимости и создаёт юниты и таймеры systemd, ссылки и автозапуск (cron скриптам
mytasks не нужен; оставшиеся от прежней установки строки crontab удаляются).
Таблица состояния — `check_mytasks.sh --status`.

Базы SQLite (`state/system_monitor.db`, `music_downloader/music_downloader.db`, `utility_bills/utility_bills.db`) создаёт `check_mytasks.sh` — задания «база данных» после venv — сразу в текущей схеме. При переносе с другой машины сначала на старой машине скопируйте прежние базы командой `sqlite3 <база> ".backup '<копия>'"` и положите копии по тем же путям ДО первого запуска `check_mytasks.sh` и таймеров; иначе создадутся пустые базы и история (опросы, список скачанного, квитанции) начнётся заново. Существующую базу `check_mytasks.sh` приводит к текущей схеме теми же командами `--migrate-db`.

## Конфигурационные файлы

Конфигурационные файлы скриптов находятся в папке `conf/` в корне репозитория.

Скрипты, использующие конфигурацию, создают каталог `conf/` при первом запуске,
если его ещё нет. Рабочие `*.conf` содержат машинно-зависимые пути и параметры,
поэтому не коммитятся; в репозитории хранятся безопасные `*.conf.example`.

Актуальные шаблоны:

- `audio_to_mp3.conf.example`;
- `auto_delete_old_files.conf.example`;
- `btrfs_monitor.conf.example`;
- `check_backups.conf.example`;
- `check_mytasks.conf.example`;
- `cloud_backup_qnap.conf.example` (только для QNAP);
- `doc2fb2.conf.example`;
- `getip.conf.example`;
- `llamactl.conf.example`;
- `log_template.conf.example`;
- `music_downloader.conf.example`;
- `utility_bills.conf.example`;
- `sources.conf.example`;
- `split_by_dash.conf.example`, `split_by_dash.keep.conf.example`;
- `system_monitor.conf.example`.

Рабочие конфиги создаёт мастер `check_mytasks.sh` (при первом запуске или
`check_mytasks.sh --configure`): для каждого отсутствующего конфига окно с
описанием из комментариев примера и значениями по умолчанию — принять всё,
настроить каждое значение или не создавать. Плейсхолдеры `@MYTASKS_DIR@`
(каталог репозитория) и `@HOME@` в примерах и шаблонах `systemd/` мастер
заменяет сам; при ручном копировании шаблона без суффикса `.example`
замените их локальными путями. `all_to_mp3.sh` при необходимости читает
`conf/audio_to_mp3.conf`; его параметры перечислены в разделе скрипта ниже.

## Актуальный формат shell-скриптов

Shell-скрипты в корне репозитория используют общие соглашения:

- Единая структура секций: `SCRIPT ID / PATHS`, `HELPERS`, `ARGS`, `MAIN`
- Явные проверки параметров и зависимостей
- Безопасные режимы запуска shell (`set -eu` или `set -uo pipefail` в зависимости от логики скрипта)
- для скриптов с JSONL-логированием — каталог `logs/` (переопределяется переменной окружения `MYTASKS_LOG_DIR`; тесты направляют её во временный каталог) и одна JSON-запись на строку;
- ротация логов по параметру конкретного скрипта либо по встроенному лимиту.
- **обязательный режим `--dry-run`** (короткая форма `-n`, если она не занята): каждый скрипт (`.sh` и `.py`) принимает его, ничего не меняет (файлы, каталоги, БД, сервисы, систему, сеть) и печатает план действий строками `[dry-run] будет: …`; чтение и проверки выполняются как обычно. У скриптов, которые только опрашивают состояние (мониторы), режим не пишет в БД/отчёты и не шлёт уведомления. Эталонная реализация — `split_by_dash.sh` (`log_action`, `DRY_RUN`, обёртки над `mkdir`/`mv`/`rmdir`). Режим описывается в разделе скрипта и покрывается bats-тестом «состояние не изменилось». Режим реализован во всех корневых скриптах; служебные логи самого запуска (`logs/*.jsonl`) допускаются и в dry-run.
- **Порядок запуска: сначала `--dry-run`.** Любой скрипт, меняющий данные (файлы, каталоги, БД, сервисы, систему), перед боевым запуском всегда выполняется с `--dry-run` на тех же аргументах и том же конфиге; вывод плана просматривается (число и состав изменений, спорные и отклонённые операции, удаления) и только после этого запускается без `--dry-run`. Это обязательно для людей и для ИИ-агентов; агент сначала получает успешный dry-run и только потом предлагает пользователю решение с итогом dry-run; при ручной отладке на боевых данных (`/mnt/copy/Music`, `/mnt/copy/Books`, бэкапы, БД) — тоже. Если результат dry-run не совпадает с ожиданиями, боевой запуск не выполняется. Планируемые по расписанию запуски (cron, systemd) идут сразу в боевом режиме, поэтому новая логика сначала проверяется вручную.

### Единый шаблон логов

Шаблон — `conf/log_template.conf` (пример для коммита: `conf/log_template.conf.example`).
Shell-скрипты с JSONL-логированием читают его, если он доступен, и пишут
унифицированные поля, подходящие для ELK/OpenSearch, Loki, Graylog и Splunk
(`@timestamp`, `schema.version`, `compat.targets`, `log.level`, `message`,
`event.action`, `service.name`), плюс служебные поля совместимости
(`script`, `event`, `msg`, `detail`, `rc` и т.д.), чтобы не ломать
существующие разборщики.

Значения полей экранирует `json_escape` (во всех shell-скриптах с JSONL-логом): `\` и `"` — с обратной косой
чертой, табуляция — `\t`, перевод строки — `\n`, прочие управляющие символы, включая `\r`, — `\u00XX`.
Поэтому имя файла с переводом строки не ломает JSONL: одна запись остаётся одной строкой.

В том же файле задаётся `KEEP_LOGS` — сколько последних JSONL-логов каждого
скрипта хранить (по умолчанию 10); скрипт может переопределить значение в своём
`conf/<скрипт>.conf`.

## Скрипты

### `all_to_mp3.sh`

Пакетная конвертация аудиофайлов в MP3 с помощью `ffmpeg`.

**Возможности:**
- Поддерживает любые форматы, распознаваемые `ffprobe`
- Обработка файлов в несколько потоков (`xargs -P`)
- Встраивает обложку — внешнюю (cover.jpg, folder.jpg, front.jpg) или встроенную в аудио
- Сохраняет структуру каталогов в выходной папке
- Значения конфига передаются дочерним процессам через окружение, `QUALITY` — только цифра 0..9
- Ведёт отчёт (`audio_to_mp3_report.txt`) и лог ошибок (`audio_to_mp3_errors.log`)

**Конфигурация** (опциональный файл `conf/audio_to_mp3.conf`, образец `conf/audio_to_mp3.conf.example`):

| Параметр     | По умолчанию         | Описание                              |
|--------------|----------------------|---------------------------------------|
| `FORMATS`    | *(все форматы)*      | Список расширений для обработки       |
| `QUALITY`    | `0`                  | Качество MP3 (0 — наилучшее)          |
| `COVER_NAMES`| `cover.jpg folder.jpg front.jpg` | Имена файлов обложек   |
| `JOBS`       | `nproc`              | Количество параллельных потоков       |
| `OUTPUT_DIR` | `/mnt/copy/Music`    | Папка для результата (структура подпапок источника сохраняется) |
| `ERROR_LOG`  | `audio_to_mp3_errors.log` | Имя журнала ошибок (создаётся внутри `OUTPUT_DIR`) |
| `REPORT_FILE`| `audio_to_mp3_report.txt` | Имя отчёта о конвертации (создаётся внутри `OUTPUT_DIR`) |

**Использование:**
```sh
./all_to_mp3.sh /путь/к/музыке
```

**Режим dry-run:** `-n, --dry-run` — только перечисляет файлы, которые были бы сконвертированы (`[dry-run] будет: конвертация …`) и неподдерживаемые; `OUTPUT_DIR`, отчёт и лог ошибок не создаются и не изменяются.

### `cloud_backup_qnap.sh`

Резервное копирование `/opt/esimych-cloud` с удалённого сервера через WireGuard VPN. Скрипт запускается **на самом QNAP NAS** (Entware cron / Task Scheduler) без `sudo`; вокруг копирования выполняет на `REMOTE_HOST` `docker compose down`/`up -d`. Подключение к серверу — по SSH-ключу (`REMOTE_SSH_KEY`); пароль используется только при наличии `sshpass`.

**Особенности:**
- Shebang `#!/opt/bin/bash` — Entware bash напрямую (штатный `/bin/sh` на QTS не поддерживает массивы/`local`/`${!var}`)
- `PATH` дополняется `/opt/sbin:/opt/bin` (Entware), т.к. QTS не содержит `wg-quick`, `wg`, `zstd`
- Нет sudo-кода — Task Scheduler/cron на QNAP и так выполняют скрипт от root
- **WireGuard поднимается в обход `wg`/`wg-quick`** — на части моделей QTS (проверено на ядре 4.2.8 aarch64) консольная утилита `wg(8)` не работает в принципе (`Protocol not supported`), поэтому туннель поднимается напрямую через userspace UAPI-сокет `wireguard-go` (см. `wg_up_userspace`/`wg_conf_get` в коде)
- Основной способ аутентификации — SSH-ключ (`REMOTE_SSH_KEY`); пароль
  используется только если одновременно заданы `REMOTE_PASSWORD` и доступен
  `sshpass`
- Автоматически переподключает bind-mount `/opt` → `ENTWARE_DATA_DIR`, если он слетел после перезагрузки NAS (`ensure_entware_mount`)
- Очистка корзины и версий Nextcloud (`occ trashbin:cleanup`, `occ versions:cleanup`) пропускается полностью: приложения `files_trashbin` и `files_versions` отключены (`occ app:disable`), в логе — события `occ_trashbin_skipped` и `occ_versions_skipped`
- При доступном `zstd` удалённый поток сжимается командой `zstd -5 --threads=0 -c`: уровень 5 выбран как компромисс между дополнительным сжатием и нагрузкой на удалённый сервер; при отсутствии `zstd` сохраняется автоматический переход на `pigz -1` или `gzip -1`

**Предварительная настройка на QNAP** (разово, вручную) подробно описана в шапке самого скрипта: установка Entware, пакетов (`opkg install bash wireguard-tools wireguard-go ncat xxd zstd coreutils-stat`), создание конфига WireGuard-клиента с отдельным peer/IP, проверка userspace UAPI-сокета, копирование SSH-ключа на сервер, заполнение `conf/cloud_backup_qnap.conf` и (опционально, только для `RAW_TRANSFER_ENABLED="1"`) открытие порта передачи в фаерволе удалённого сервера — см. шаг 8 в шапке скрипта.

**Конфигурация** (`conf/cloud_backup_qnap.conf`, см. `.example`):

| Параметр          | По умолчанию               | Описание                                       |
|-------------------|-----------------------------|------------------------------------------------|
| `WG_INTERFACE`    | *(обязательно)*             | Имя WireGuard-интерфейса (напр. `wg0-qnap`)    |
| `WG_CONF_FILE`    | `/opt/etc/wireguard/<WG_INTERFACE>.conf` | Путь к конфигу WireGuard на QNAP |
| `WG_SOCK`         | `/var/run/wireguard/<WG_INTERFACE>.sock` | UAPI-сокет `wireguard-go` (его же подменяют тесты) |
| `WG_ENDPOINT`     | *(пусто)*                   | Необязательное переопределение публичного endpoint WireGuard в формате `IPv4:port`; если пусто, берётся `Endpoint` из `/opt/etc/wireguard/<WG_INTERFACE>.conf` |
| `ENTWARE_DATA_DIR`| `/share/Public/entware`     | Постоянный каталог Entware, который скрипт при необходимости подключает в `/opt` |

| `OPTIMIZE_MARIADB_BEFORE_BACKUP` | `0`       | Выполнить оптимизацию MariaDB перед архивом    |
| `MARIADB_SERVICE_NAME`           | `mariadb` | Имя MariaDB-сервиса в `docker compose`         |

| `COMP_PIGZ_CMD`                  | `pigz -1` | Команда сжатия на удалённом сервере при наличии `pigz` |
| `COMP_GZIP_CMD`                  | `gzip -1` | Команда сжатия на удалённом сервере (запасной вариант) |

**Безопасность:**
- `NEXTCLOUD_SERVICE_NAME`, `MARIADB_SERVICE_NAME` проверяются по шаблону `A-Za-z0-9._-`; `REMOTE_HOST` — по `A-Za-z0-9._:-` (двоеточие для IPv6); `REMOTE_PATH` — абсолютный путь из `A-Za-z0-9._/-`. Значения, которые не подходят, останавливают скрипт до начала работы.
- `umask 022`: архивы и логи читаются всеми (их читает `check_backups.sh` по NFS), но записывает только владелец. Временные файлы raw-transfer на удалённом сервере создаются через `mktemp`.

**Логи:** JSONL-файл `logs/cloud_backup_qnap-YYYY-MM-DD-HH-MM-SS.jsonl` на QNAP. Хранится `BACKUP_KEEP_COUNT` последних файлов (см. `cleanup_logs`, тот же параметр, что и для архивов).

**Диагностика скорости:** перед передачей и во время неё скрипт фиксирует
сетевой тест, RTT, load average, доступную память и IO QNAP. Итоговое событие
`backup_metrics` содержит размер, длительность, среднюю скорость и агрегированные
ресурсные показатели. При скорости ниже
`BACKUP_DEGRADATION_MIBS_THRESHOLD` создаётся `backup_degradation` с вероятной
причиной. Ошибки raw-transfer дополняются снимком состояния удалённого сервера.

После бэкапа `docker compose up -d` и состояние контейнеров проверяются до `SERVICES_START_RETRIES` раз. Сбоем считаются контейнеры в состоянии `unhealthy`, `dead`, `restarting` или `Exited` с ненулевым кодом; `Exited (0)` (контейнеры-сироты удалённых из compose сервисов, одноразовые init-контейнеры) сбоем не считается. Если после всех попыток сбойные контейнеры остаются, в лог записывается `docker compose ps -a`, а сам скрипт завершается с ненулевым кодом.

**Передача в обход SSH-шифрования (`RAW_TRANSFER_ENABLED`):** при значении
`1` сжатый поток передаётся через сырой TCP внутри WireGuard-туннеля, без
дополнительного SSH-шифрования. WireGuard продолжает обеспечивать
конфиденциальность и целостность; SSH используется для управляющих команд и
запуска листенера.

Для корректного завершения потока используются:
- удалённая сторона: **`nc -N -l ...`** — без флага `-N` OpenBSD nc не закрывает сокет по EOF своего stdin и висит до `RAW_TRANSFER_REMOTE_TIMEOUT_SEC` (часы) вместо того, чтобы завершиться сразу после отправки всех данных;
- сторона QNAP: **`ncat --recv-only ... < /dev/null`** — флаг запрещает
  отправку локального stdin, а перенаправление позволяет процессу завершиться
  после получения EOF от сервера.

Порт `RAW_TRANSFER_PORT` нужно открыть в фаерволе удалённого сервера. При
недоступности `nc` или исчерпании попыток подключения скрипт автоматически
переходит на SSH-передачу.

Raw TCP не имеет собственного шифрования и аутентификации: защиту даёт только WireGuard. Включайте
`RAW_TRANSFER_ENABLED=1`, только если все пиры WireGuard доверенные; правило фаервола в шапке скрипта
ограничивает порт подсетью WireGuard. Файлы статуса и ошибок на удалённом сервере создаются через `mktemp`
(`/tmp/.<имя>-raw-status.XXXXXX`); если это не удалось, передача идёт через SSH (`raw_transfer_mktemp_failed`).

**Имя архива:** `cloud_backup_qnap-YYYY-MM-DD.tar.zst` или `cloud_backup_qnap-YYYY-MM-DD.tar.gz`.

**Поведение при существующем архиве:**
- `tar.gz` и `tar.zst` проверяются на целостность перед дозаписью (`gzip -t` / `zstd -t`)
- валидный архив за текущую дату дополняется новым сжатым потоком
- битый или пустой архив удаляется и пересоздаётся
- если утилита проверки (`gzip` или `zstd`) недоступна, скрипт не дозаписывает, а создаёт архив заново

**Встроенные исключения при архивировании (всегда включены):**
- `tmp/*`, `cache/*`, `.cache/*` в корне `REMOTE_PATH`
- `data/*/uploads/*`
- `data/*/files_trashbin/uploads/*`
- `data/*/cache/*`
- `data/appdata_*/preview/*`
- `data/appdata_*/thumbnails/*`
- `data/appdata_*/css/*`
- `data/appdata_*/js/*`

Эти excludes жёстко заданы в скрипте и не настраиваются через `conf/cloud_backup_qnap.conf`.

**Планирование запуска на QNAP** — `crontab` QNAP. `crond` (BusyBox) читает live-файл `/tmp/cron/crontabs/admin` на tmpfs, а постоянная копия `/etc/config/crontab` пересоздаёт его при загрузке, поэтому строки добавляются в `/etc/config/crontab` и применяются `crontab`:
```sh
vi /etc/config/crontab
# бэкап каждый день в 04:00:
0 4 * * * /opt/bin/bash /share/Public/tasks/cloud_backup_qnap.sh >/dev/null 2>&1
# Entware не поднимается автозапуском QTS — возвращать bind-mount /opt раз в минуту:
* * * * * [ -x /opt/bin/opkg ] || mount --bind /share/Public/entware /opt
crontab /etc/config/crontab
/etc/init.d/crond.sh restart
```

**Важно:** не вызывайте скрипт через `sh`: системный `/bin/sh` QTS — не bash, а явный `sh …` игнорирует шебанг `#!/opt/bin/bash`.

**Режим dry-run:** `-n, --dry-run` — печатает план без изменений: `/opt` Entware не монтируется, WireGuard не поднимается (если интерфейс неактивен, проверки удалённого сервера пропускаются), замер скорости сети и диагностика нагрузки не запускаются, сервисы не останавливаются, архив не создаётся, файл состояния оптимизации БД не обновляется; показываются компрессор, режим дозаписи и старые копии, которые были бы удалены.

### `auto_delete_old_files.sh`

Автоматически удаляет старые файлы по сроку хранения из указанных каталогов.

**Конфигурация** (`conf/auto_delete_old_files.conf`):

| Параметр      | По умолчанию     | Описание |
|---------------|------------------|----------|
| `TARGET_DIRS` | *(обязательно)*  | Каталоги для очистки: один путь на строку; пустые строки игнорируются, пробелы в путях поддерживаются |
| `FILE_TYPES`  | `all`            | Типы файлов: `all` или список расширений (`log,tmp,bak`) |
| `KEEP_DAYS`   | `30`             | Сколько дней хранить файлы |

**Правило удаления:** все заданные каталоги сначала нормализуются и проверяются: они должны существовать, не быть `/`, домашним каталогом или каталогом глубины менее двух. Только после успешной проверки всего списка удаляются файлы (`-type f`) старше `KEEP_DAYS` дней; перехода на другие файловые системы нет (`-xdev`). Имена файлов обрабатываются через NUL-разделитель, поэтому пробелы и переводы строк не могут изменить границы пути.

**Использование:**
```sh
./auto_delete_old_files.sh
```

**Расписание:** не ставится; при необходимости — user-таймер systemd по образцу `systemd/user/*.timer` (cron скриптам mytasks не нужен).

**Режим dry-run:** `-n, --dry-run` — перечисляет файлы, которые были бы удалены (`[dry-run] будет: удалён файл: …`), ничего не удаляя; в конце печатает число подошедших файлов.

### `check-store-mount.sh`

Проверяет, смонтированы ли все точки монтирования из `/etc/fstab`.

**Возможности:**
- Пропускает виртуальные ФС (`/proc`, `/sys`, `/dev`, `swap` и др.)
- При обнаружении несмонтированных точек отправляет desktop-уведомление через `notify-send`
- Дублирует сообщение в консоль
- Запускается при входе в графический сеанс user-юнитом `systemd/user/check-store-mount.service` (устанавливает `check_mytasks.sh`)

**Конфигурация** (необязательно, `conf/check-store-mount.conf`, пример — `conf/check-store-mount.conf.example`; значения можно передать и окружением):

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `MOUNT_WAIT_SECS` | `30` | Максимальное ожидание монтирования точки, с (должно совпадать с `x-systemd.mount-timeout` в `/etc/fstab`) |
| `MOUNT_PROBE_TIMEOUT_SECS` | `5` | Тайм-аут обращения к каталогу (запускает автомонтирование), с |
| `MOUNT_POLL_SECS` | `3` | Пауза между проверками точки, с |
| `MOUNT_IGNORE_REGEX` | `^/(proc\|sys\|dev\|run\|tmp\|boot)` | Точки из `/etc/fstab`, которые не проверяются (расширенное регулярное выражение) |
| `FSTAB_FILE` | `/etc/fstab` | Таблица точек монтирования для проверки; не читается — код `2` и событие `fstab_unreadable` |
| `KEEP_LOGS`, `APP_NAME`, `ICON_NAME`, `URGENCY` | `10`, `MountCheck`, `drive-harddisk`, `critical` | Хранение логов и параметры уведомления |

**Использование:**
```sh
./check-store-mount.sh
```

**Режим dry-run:** `-n, --dry-run` — проверка выполняется как обычно, но уведомление `notify-send` не отправляется, а только печатается.

### `check_backups.sh`

Проверяет каталоги с архивами резервных копий и пишет результат в JSONL-лог; при любой ошибке дополнительно показывает уведомление в трее (`notify-send`).

**Что проверяется для каждого каталога из `BACKUP_DIRS`:**
- каталог доступен и читаем (обращение запускает автомонтирование NFS; зависание ограничено `ACCESS_TIMEOUT_SECS`);
- в нём есть архивы по маскам `ARCHIVE_PATTERNS` (по умолчанию `*.tar.zst *.tar.gz *.tgz *.tar *.zip *.7z`);
- самый свежий архив не старше `MAX_AGE_DAYS` (для записи `каталог|N` — свой лимит) и не меньше `MIN_SIZE_BYTES`;
- размер свежего архива не упал ниже `MIN_SIZE_RATIO_PCT` % от предыдущего (признак оборванной записи);
- целостность свежего архива при `VERIFY_INTEGRITY="yes"` (по умолчанию включено; `zstd -t`, `gzip -t`, `unzip -t`, `7z t`, `tar -t`). Архив читается целиком, на NFS ~112 МБ/с архив ~33 ГБ проверяется ≈5 минут (замер 2026-10-04): проверка идёт с `nice -n 19`/`ionice -c3`, тайм-аут рассчитывается по размеру (`размер / VERIFY_MIN_SPEED_MBPS + VERIFY_TIMEOUT_BASE_SECS`, для 33 ГБ ≈28 мин; превышение — только WARN в логе), уже проверенный и неизменившийся архив повторно не читается (`state/check_backups.verified`), а изменённый менее `VERIFY_MIN_AGE_MINUTES` назад (ещё пишется) откладывается до следующего запуска;
- недописанный архив не считается ошибкой (событие `archive_writing`, код возврата не меняется). Последний архив моложе `WRITING_RECENT_MINUTES` замеряется дважды с паузой `WRITING_CHECK_SECS`; если размер/mtime растут или файл открыт на запись локальным процессом (`lsof`), он пропускается, а возраст, размер и целостность проверяются у предыдущего готового архива (`cloud_backup_qnap.sh` пишет сразу под финальным именем; удалённого писателя по NFS, например QNAP, видно только по росту файла). Растущий временный файл «маска + суффикс из `PARTIAL_SUFFIXES`» (`sources.sh` пишет `*.7z.part`) превращает «архив устарел» в предупреждение `archive_stale_writing`. Если архив изменился во время проверки целостности, «повреждён» не засчитывается. Если готовых архивов ещё нет, а первый пишется, — каталог в порядке.

**Конфигурация:** `conf/check_backups.conf` (пример: `conf/check_backups.conf.example`).

**Настройки (conf/check_backups.conf):** `NOTIFY_ENABLED` (`yes`) — уведомление в трее (флаг `--no-notify` главнее); `VERIFY_NICE_LEVEL` (19) — `nice` при проверке целостности; `VERIFIED_KEEP` (50) — сколько проверенных архивов помнить в `state/check_backups.verified`.

**Коды возврата:** `0` — всё в порядке, `1` — найдены проблемы с бэкапами, `2` — ошибка конфигурации, зависимостей или аргументов (уведомление показывается и в этом случае).

**Использование:**
```sh
./check_backups.sh              # проверка + лог + уведомление при ошибках
./check_backups.sh --no-notify  # без уведомления в трее
```

**Расписание — systemd user timer** (уведомлению нужна сессия пользователя, поэтому юниты пользовательские). Таймер срабатывает через 4 минуты после загрузки системы (если сеанс начался позже — сразу после входа) и далее раз в сутки при непрерывной работе (`OnBootSec=4min`, `OnUnitActiveSec=1d`). Юниты: `systemd/user/check-backups.{service,timer}`.

Устанавливает и включает их `check_mytasks.sh` (шаблоны с подстановкой `@MYTASKS_DIR@`).

```sh
./check_mytasks.sh               # установить/обновить юниты (с вопросом)

# Проверка
systemctl --user list-timers check-backups.timer
journalctl --user -u check-backups.service -n 20
```

**Режим dry-run:** `-n, --dry-run` — проверки выполняются как обычно, но кэш проверенных архивов (`state/check_backups.verified`) не изменяется, `state/` не создаётся, уведомление не показывается (печатается).

### `check_mytasks.sh`

Стартовая настройка mytasks на машине и регулярная проверка его сервисов и заданий.

**Порядок работы:**
1. Определяет семейство ОС по `/etc/os-release` (сначала `ID`, затем `ID_LIKE`):

   | Семейство | Дистрибутивы (примеры) | Пакеты | Обновление системы |
   |---|---|---|---|
   | `arch` | Arch, Garuda, Manjaro, EndeavourOS, CachyOS, Artix, ArcoLinux, SteamOS | `pacman` | Garuda — `garuda-update --noconfirm`, иначе `pacman -Syu` |
   | `debian` | Debian, Ubuntu (и *buntu), Mint/LMDE, Pop!_OS, elementary, Zorin, KDE neon, MX, Kali, Deepin, Devuan, Raspberry Pi OS | `apt-get` | `apt-get update && apt-get -y full-upgrade` |
   | `redhat` | Fedora, RHEL, CentOS Stream, Rocky, Alma, Oracle, Amazon, Nobara, Mageia; Fedora Atomic (Silverblue, Kinoite, Bazzite) | `dnf`/`yum`; Atomic — `rpm-ostree` | `dnf -y upgrade --refresh` / `yum -y update` / `rpm-ostree upgrade` |
   | `suse` | openSUSE Leap/Tumbleweed/Slowroll, SLES; MicroOS — `transactional-update` | `zypper` | Tumbleweed/Slowroll — `zypper dup`, Leap/SLES — `zypper update` |
   | `alpine` | Alpine, postmarketOS (без systemd) | `apk` | `apk update && apk upgrade` |
   | `void` | Void (runit) | `xbps-install` | `xbps-install -Syu xbps && xbps-install -Syu` |
   | `gentoo` | Gentoo, Funtoo, Calculate | `emerge` | `emaint sync -a && emerge -uDN @world` (может идти часы) |
   | `solus` | Solus | `eopkg` | `eopkg upgrade -y` |
   | `nixos` | NixOS — пакеты и службы объявляются в `configuration.nix`, автоустановка пакетов отключена | — | `nixos-rebuild switch --upgrade` |

   Нераспознанная ОС — явное предупреждение с её `ID`/`ID_LIKE`: пакеты ставятся вручную либо семейство задаётся в `OS_FAMILY`. Без systemd юниты не создаются (службы включаются средствами своего init).

   **Alpine / postmarketOS:** скрипты mytasks на Bash, а в Alpine по умолчанию только busybox — перед первым запуском выполните `apk add bash`; GNU `find`/`coreutils` (нужны `find -printf`, `stat -c` и т.п.) скрипт проверит как зависимости `gnu:find`/`gnu:stat` и предложит `findutils`/`coreutils`. **NixOS:** нет `/bin/bash`, `/usr/bin/python3`, `/usr/bin/sleep` — шебанги и юниты mytasks используют `/usr/bin/env`; пакеты объявляйте в `configuration.nix`.
2. **Обязательно обновляет систему** штатной командой своего семейства (столбец «Обновление системы»; одно повышение прав) — до любых изменений. Если обновление не удалось или для ОС не поддерживается, пакеты в этом запуске не ставятся (в rolling-дистрибутивах установка без обновления — неподдерживаемое частичное обновление), остальные проверки идут. После обновления ядра или при флаге `/run/reboot-required` скрипт напоминает о перезагрузке. В режимах `--status`, `--no-create` и без терминала/окон без `--yes` обновление не выполняется; `GARUDA_UPDATE="no"` — на Garuda чистый `pacman -Syu` вместо `garuda-update`.
3. Затем прописывает себя в автозагрузку: user-юнит `check-mytasks.service` при входе в графический сеанс запускает `check_mytasks.sh --no-create --notify` (таблица в журнале и уведомление о проблемах).
4. Записывает каталог mytasks — каталог, откуда запущен скрипт, — в `conf/check_mytasks.conf` (`MYTASKS_DIR`). Если репозиторий перенесён и каталог в конфиге другой, предупреждает и предлагает обновить его, а затем и все юниты.
5. При первом запуске (нет `conf/check_mytasks.conf`) проводит мастер всех отсутствующих конфигов по `conf/*.conf.example`, `music_downloader/*.json.example` и `utility_bills/*.json.example` (кроме `cloud_backup_qnap.conf`): окна `zenity` (без него — `kdialog`), без графики — вопросы в терминале. Описание каждого значения берётся из комментариев примера, значения по умолчанию — из примера с подстановкой `@MYTASKS_DIR@`/`@HOME@`. Строки примера без изменений копируются как есть (`${HOME}` и т.п. сохраняются).
6. Проверяет зависимости (обязательные и необязательные) и ставит пакеты менеджером своего семейства одним запросом прав.
7. Проверяет задания и для каждого отсутствующего или неработающего выводит предупреждение с описанием и вопрос «создать?»: «да» — создаёт, «нет» — ничего не меняет и в этом запуске больше не спрашивает.

Кнопки окон: **«Отмена»** относится только к текущему окну (конфиг не создаётся, поле остаётся со значением по умолчанию); **«Стоп»** (в терминале — ответ «стоп») прерывает весь процесс — дальше ничего не спрашивается и не меняется, уже сделанное остаётся, выводится итоговая таблица; продолжить — запустить скрипт снова. «Стоп» есть во всех окнах `zenity`; у `kdialog` — кнопкой в вопросах «да/нет» и пунктом «■ Стоп» в списках (в полях ввода kdialog третьей кнопки нет), поэтому `zenity` выбирается первым (`UI="kdialog"` — принудительно kdialog). Значения по умолчанию, которые можно определить на машине, мастер подставляет сам: `OS_FAMILY` — семейство по `/etc/os-release`, для `conf/llamactl.conf` — `CUDA_ARCH` (compute capability из `nvidia-smi`) и `BUILD_JOBS` (`nproc` − 2).
8. Печатает таблицу состояния в начале и (если что-то менялось) итоговую.

**Задания по умолчанию** (массив `JOBS` в начале скрипта, переопределяется в конфиге):

| Задание | Вид | Что делает |

| `getip.timer` | user-юнит | `getip.sh` через 2 мин после загрузки и каждые 30 мин |
| `crontab` | старый cron | в crontab нет строк `music_downloader.sh`, `sources.sh`, `btrfs_monitor.sh`, `getip.sh`, `utility_bills.sh` (иначе — второй, параллельный запуск); исправление — удаление строк вместе с комментарием `# mytasks:` |
| `conf/check_backups.conf`, `conf/sources.conf`, `music_downloader/music_downloader.json`, `utility_bills/utility_bills.json` | конфиг | создаются мастером |
| `music_downloader/venv`, `utility_bills/venv` | venv | `music_downloader/setup_venv.sh`, `utility_bills/setup_venv.sh` |
| `state/system_monitor.db`, `music_downloader/music_downloader.db`, `utility_bills/utility_bills.db` | база данных (`db`) | проверка — `<команда> --dry-run` (`system_monitor.sh --migrate-db`, `music_downloader.py --migrate-db`, `utility_bills.sh --migrate-db`): строка `[dry-run] будет:` — база отсутствует или устарела (ВНИМАНИЕ), иначе OK со «схема vN»; исправление — `<команда>` от пользователя; нет исполняемого файла — ВНИМАНИЕ, при исправлении «не создана: нет …» |
| `llamactl`, `llamactl-tray`, `llamactl-tray.desktop`, `llama-server.service`, `llama-fim.service` | ссылки, автозапуск, сервисы | только если есть каталог `LLAMA_PREFIX` (из `conf/check_mytasks.conf`, иначе из `conf/llamactl.conf`, иначе `/opt/llama.cpp`) |

Шаблоны юнитов и автозапуска лежат в `systemd/` (`systemd/*.service|timer` — системные, `systemd/user/` — пользовательские, `systemd/autostart/` — XDG autostart) и содержат плейсхолдер `@MYTASKS_DIR@`; установленный файл, отличающийся от отрисованного шаблона (старая версия или другой каталог), отмечается «отличается» и предлагается к обновлению. Порядок между заданиями задан `After=`: `sources.service` начинается после `music-downloader.service`, `check-backups.service` — после `sources.service` (действует и когда оба таймера догоняют пропуск сразу после загрузки). Таймеры включаются с `--now`, сервисы входа в сеанс — только `enable`.

**Таблица состояния** (`--status`): вид, задание, установлено (есть/нет/отличается/другой путь), автозапуск (включён), состояние (ожидает/работает/при событии/ошибка/не запущен), итог (`OK`, `ВНИМАНИЕ`, «не требуется») и описание; ниже — все зависимости с пакетом для текущего семейства.

**Повышение прав** (обновление системы, системные юниты, пакеты): `SUDO_CMD="auto"` — `sudo -A` при заданном `SUDO_ASKPASS`, иначе `pkexec` в графическом сеансе, иначе `sudo` в терминале. Скрипт перезапускает сам себя с внутренними командами `__root-update`, `__root-install-units`, `__root-install-file`, `__root-enable`, `__root-linger`, `__root-pkg` — один запрос пароля на действие; эти вызовы логов не пишут. Root-шаги разбираются до пользовательского конфига и проверяют аргументы (пакеты — из `DEPS`, юниты и файлы — из `JOBS`, каталоги назначения принадлежат root, linger — только для вызвавшего пользователя). Root-копии (`root-file`: `system_monitor.sh`, его конфиг, `llamactl-root`) ставятся в `ROOT_LIB_DIR` (`/usr/local/lib/mytasks`) и `ROOT_CONF_DIR` (`/etc/mytasks`); сам `check_mytasks.sh` запускается от root из домашнего каталога, как `sudo make install` — это осознанный компромисс. Подробности и порядок обновления root-копий — в разделе `llamactl` и в `ai-md/AI.md`.

**Конфигурация:** `conf/check_mytasks.conf` (пример `conf/check_mytasks.conf.example`, создаётся мастером): `MYTASKS_DIR`, `LLAMA_PREFIX`, `OS_FAMILY` (пусто — автоопределение), `SUDO_CMD`, `UI` (`auto`/`kdialog`/`tty`/`none`), каталоги `SYSTEM_UNIT_DIR`, `ROOT_LIB_DIR` (`/usr/local/lib/mytasks`, root-копии скриптов; подставляется в `@ROOT_LIB_DIR@`), `ROOT_CONF_DIR` (`/etc/mytasks`, root-копии настроек; `@ROOT_CONF_DIR@`), `USER_UNIT_DIR`, `AUTOSTART_DIR`, `BIN_DIR`, `KEEP_LOGS`, `SYSTEM_PYTHON` (пусто — `/usr/bin/python3`, где его нет — `python3` из PATH), `KERNEL_MODULES_DIR` (`/usr/lib/modules`, по нему определяется, что нужна перезагрузка после обновления ядра), параметры уведомления; при необходимости — свои массивы `JOBS` и `DEPS` (формат описан в начале скрипта). Если конфига нет, скрипт предупреждает и использует каталог запуска.

**Коды возврата:** `0` — всё на месте, `1` — есть незапущенные или не прописанные задания, конфиги или обязательные зависимости, `2` — ошибка аргументов.

**Использование:**
```sh
./check_mytasks.sh --status       # только таблица
./check_mytasks.sh --dry-run      # план: «[dry-run] будет: …»
./check_mytasks.sh                # предупреждения и вопросы «создать?» в окне
./check_mytasks.sh --yes          # создать всё без вопросов (конфиги по умолчанию, только обязательные пакеты)
./check_mytasks.sh --configure    # мастер для всех отсутствующих конфигов
./check_mytasks.sh --no-create --notify   # как в автозагрузке: без вопросов, уведомление о проблемах
```
Дополнительно: `--ask` — вопросы в терминале, даже если stdin не терминал; `--no-gui` — без окон `kdialog`/`zenity`.

**Режим dry-run:** `-n, --dry-run` — проверки и таблица как обычно; юниты, crontab, ссылки, автозапуск, конфиги и пакеты не меняются, окна не открываются; печатаются строки `[dry-run] будет: …` (для конфигов — со списком значений по умолчанию), в лог пишутся события `dry_<event>`.

### `system_monitor.sh`

Диагностика системы: жёсткие диски через SMART (`smartctl`), CPU (температура,
загрузка, load average) и GPU (NVIDIA, через `nvidia-smi`). Опрос, запись
состояния в SQLite и формирование HTML-отчёта (таблицы, диаграммы,
аналитическая справка по каждому диску). Предназначен для запуска по
расписанию и/или при загрузке системы.

**Что делает:**

Диски:
- Определяет физические диски автоматически через `lsblk` (или берёт список из `DISKS` в конфиге), пропуская `zram`, `loop`, `ram`, `sr`, `dm-`
- Опрашивает каждый диск через `smartctl -a -j` (JSON) и разбирает результат через `jq`: health, модель, серийный номер, температура, наработка (power-on hours), `Reallocated_Sector_Ct`, `Current_Pending_Sector`, `Offline_Uncorrectable` (для NVMe — соответствующие поля `nvme_smart_health_information_log`)
- Определяет устойчивое системное имя диска (`/dev/disk/by-id/...`, например `ata-ST4000DM004-2U9104_WW608PYW`) — не меняется при перестановке дисков/перезагрузке, в отличие от `/dev/sdX`; хранится в SQLite вместе с остальными метриками
- Определяет точки монтирования диска **с привязкой к разделу**: разделы — из `lsblk -J` + `jq`, точки — из таблицы монтирования хоста `findmnt --task 1` (служба работает в песочнице systemd, и своя таблица `lsblk` показала бы её bind-монтирования `…/state`, `…/logs`, второй `/var/tmp`) (например `nvme0n1p1: /, /var/log, /var/cache, /var/tmp, /root, /srv; nvme0n1p2: /boot/efi`) — на btrfs один и тот же раздел часто смонтирован сразу в несколько мест через подтома (subvolumes); JSON-разбор через `jq` берётся не случайно: построчный `lsblk -o MOUNTPOINT` (ед. число) отдаёт только одну точку на раздел и может молча потерять корень `/`
- Определяет объём диска в байтах через `lsblk -bdn -o SIZE` (не зависит от `smartctl` — доступен даже если SMART недоступен/диск не поддерживается) и показывает его в отчёте в человекочитаемом виде (КиБ/МиБ/ГиБ/ТиБ)

CPU:
- Температура — через `lm_sensors` (`sensors -j`), ищет главный тепловой датчик пакета (`Tctl`/`Tdie` на AMD, `Package id 0` на Intel); **опционально** — если `sensors` не установлен/не настроен, CPU всё равно опрашивается, просто без температуры
- Загрузка (%) — две выборки `/proc/stat` с интервалом в 1 секунду (тот же принцип, что использует `top`/`mpstat`), без дополнительных зависимостей
- Load average (1/5/15 мин) — из `/proc/loadavg`

GPU (NVIDIA):
- Через `nvidia-smi --query-gpu=... --format=csv`: модель, температура, загрузка (%), использование видеопамяти, потребляемая мощность — по каждой видеокарте отдельно (поддержка нескольких GPU)
- **Опционально** — если `nvidia-smi` не найден (нет NVIDIA GPU или драйвера), опрос GPU просто пропускается, это не ошибка

Отчёт и хранение:
- Пишет каждый опрос как строки в таблицы `disk_stats`/`cpu_stats`/`gpu_stats` в SQLite (`DB_FILE`), не перезаписывая историю — на её основе строятся графики. **Все данные, которые попадают в отчёт, сначала сохраняются в SQLite** (ничего не вычисляется «на лету» только для HTML) — это сделано специально, чтобы дальше можно было строить аналитические отчёты поверх накопленной истории
- Формирует HTML-отчёт целиком из данных SQLite: сводные плитки (кол-во объектов в норме/внимание/критично по дискам+CPU+GPU вместе), таблица метрик по каждому диску (с колонками «Точка монтирования» и «Объём»), **аналитическая справка** по каждому диску (деградация поверхности, риск отказа, перегрев, точки монтирования и т.д.), таблицы и графики по CPU и GPU, график истории температуры дисков и диаграмма Reallocated/Pending-секторов — всё встроенным SVG, без внешних JS-библиотек. Графики CPU/GPU совмещают температуру (°C) и проценты (загрузка, VRAM) на одной общей шкале 0-100 — это не «две оси», а честно общий диапазон, единица измерения проставлена у каждой точки
- При критическом состоянии любого объекта (диск: SMART FAILED/неисправимые ошибки чтения/температура выше `TEMP_CRIT_C`, у NVMe — `NVME_TEMP_CRIT_C`; CPU/GPU: температура выше `CPU_TEMP_CRIT_C`/`GPU_TEMP_CRIT_C`) отправляет desktop-уведомление через `notify-send` (как `btrfs_monitor.sh` / `check-store-mount.sh`) и завершается с кодом `1`; предупреждения (переназначенные/ожидающие секторы диска, температура выше порога «внимание») только пишутся в лог, без уведомления
- Ротирует и JSONL-логи (`KEEP_LOGS`), и HTML-отчёты (`REPORT_KEEP`)
- **Версия схемы БД** — `PRAGMA user_version` (сейчас 1). Новая база создаётся сразу в текущей схеме. База со схемой старше v1 не поддерживается: обычный запуск завершается ошибкой без изменений, `--dry-run` предупреждает. Владелец файла БД определяется `FILE_OWNER` (см. таблицу настроек).

**Конфигурация:**
- `conf/system_monitor.conf`
- пример: `conf/system_monitor.conf.example`

| Параметр        | По умолчанию                    | Описание |
|-----------------|----------------------------------|----------|
| `DISKS`         | *(пусто = автоопределение)*      | Список дисков через запятую (`sda,sdb`), пусто — автоопределение через `lsblk` |
| `DB_FILE`       | `state/system_monitor.db`        | Путь к базе SQLite с историей опросов |
| `FILE_OWNER`    | владелец:группа каталога скрипта | Кому передаются файлы скрипта (БД, логи, отчёты, `latest.html`): `пользователь` или `пользователь:группа`. Скрипт работает от root; не от root ничего не меняется. Прежние файлы приводятся к этому владельцу при каждом запуске под root. Пусто = владелец каталога скрипта |
| `REPORT_DIR`    | `system_reports/` рядом со скриптом | Каталог для HTML-отчётов |
| `REPORT_KEEP`   | `5`                               | Сколько последних HTML-отчётов хранить |
| `KEEP_LOGS`     | `10`                              | Сколько последних JSONL-логов хранить |
| `HISTORY_POINTS`| `30`                              | Сколько последних опросов показывать на графиках истории |
| `SMARTCTL_BIN`  | `smartctl`                        | Путь к бинарю `smartctl`, если не в `PATH` |
| `SENSORS_BIN`   | `sensors`                         | Путь к бинарю `sensors` (lm_sensors), если не в `PATH`; опционально |
| `NVIDIA_SMI_BIN`| `nvidia-smi`                      | Путь к бинарю `nvidia-smi`, если не в `PATH`; опционально |
| `SMARTCTL_OPTS` | `-a -j -d auto`                  | Опции `smartctl`; `-j` (JSON) обязателен, иначе разбор не работает |
| `CPU_SAMPLE_SECS` | `1`                            | Интервал между двумя выборками `/proc/stat` для загрузки CPU, с |
| `TEMP_WARN_C`, `TEMP_CRIT_C` | `50`, `60`           | Пороги температуры дисков (°C) для «внимание»/«критично» |
| `NVME_TEMP_WARN_C`, `NVME_TEMP_CRIT_C` | пусто (в примере `70`, `80`) | Отдельные пороги для NVMe (`/dev/nvme*`), которым штатно теплее SATA; пусто — общие `TEMP_*` |
| `CPU_TEMP_WARN_C`, `CPU_TEMP_CRIT_C` | `80`, `90`   | Пороги температуры CPU (°C) |
| `GPU_TEMP_WARN_C`, `GPU_TEMP_CRIT_C` | `75`, `85`   | Пороги температуры GPU (°C) |
| `APP_NAME`, `ICON_NAME`, `URGENCY` | `SystemMonitor`, `utilities-system-monitor`, `critical` | Параметры desktop-уведомления |

**Использование:**
```sh
# Опрос дисков/CPU/GPU + запись в SQLite + HTML-отчёт
sudo ./system_monitor.sh

# Только пересобрать HTML-отчёт из уже накопленных данных, без опроса
sudo ./system_monitor.sh -r

# Только создать базу или привести её схему к текущей, без опроса (--migrate-db; с -n — план; несовместим с -r/--report)
./system_monitor.sh --migrate-db

# Явный конфиг (таймер передаёт root-конфиг)
sudo ./system_monitor.sh -c /etc/mytasks/system_monitor.conf
```

**Важно:** для чтения SMART-атрибутов `smartctl` обычно требует root, поэтому
скрипт запускается от root; CPU/GPU опрашиваются в том же запуске. От root
скрипт отказывает, если в путях каталогов данных или у файлов БД есть симлинк;
`latest.html` пишется через временный файл и `mv`. Ключ `-c, --config ФАЙЛ`
задаёт конфиг явно (без ключа: root-копия — только `/etc/mytasks/system_monitor.conf`).

**Расписание — системный systemd timer:** шаблоны `systemd/system-monitor.service`
и `systemd/system-monitor.timer` (плейсхолдер `@MYTASKS_DIR@`) устанавливает в
`/etc/systemd/system` и включает `check_mytasks.sh`. Юнит запускает root-копию
`/usr/local/lib/mytasks/system_monitor.sh --config /etc/mytasks/system_monitor.conf`
в песочнице systemd (запись только в `state/`, `logs/`, `system_reports/` каталога
mytasks); изменения скрипта и `conf/system_monitor.conf` действуют после «обновить»
в `check_mytasks.sh`. Таймер срабатывает в 00/06/12/18 часов, а благодаря `Persistent=true` пропущенный слот (машина была
выключена) выполняется при первой же загрузке — не более одного раза за интервал.

```sh
./check_mytasks.sh                         # установить/обновить и включить (с вопросом)

# Проверка
systemctl list-timers system-monitor.timer
journalctl -u system-monitor.service -n 20
```

Актуальный отчёт всегда доступен по стабильному пути `system_reports/latest.html`;
предыдущие версии хранятся как `system_reports/system_monitor-<timestamp>.html`
(не более `REPORT_KEEP` штук).

**Режим dry-run:** `-n, --dry-run` — диски, CPU и GPU опрашиваются, но запись в SQLite, `init_db`, HTML-отчёт (`latest.html`), ротация отчётов и уведомления не выполняются; вместо записей печатаются строки `[dry-run] будет: запись в … `. Критическое состояние в этом режиме не оценивается (оно считается по БД при формировании отчёта).

### `doc2fb2.sh`

Рекурсивная конвертация DOC / DOCX / RTF / ODT → FB2.

**Цепочки конвертации:**
- `docx`, `odt` → pandoc → fb2
- `doc`, `rtf` → LibreOffice → odt → pandoc → fb2
- Fallback для `rtf`: pandoc напрямую, затем `unrtf` → txt → pandoc
- Fallback для `doc`: `antiword` / `catdoc` / `wvText` → txt → pandoc

**Ключевые опции:**

| Опция               | Описание                                              |
|---------------------|-------------------------------------------------------|
| `-d, --dir DIR`     | Исходный каталог (обязательно)                        |
| `-o, --out OUTDIR`  | Выходной каталог                                      |
| `-n, --dry-run`     | Без изменений, только показать                        |
| `--overwrite`       | Перезаписывать существующие FB2                       |
| `--skip-newer`      | Пропускать, если FB2 новее источника                  |
| `--exclude PATTERN` | Исключить файлы по маске (можно несколько раз)        |
| `--only doc|docx|rtf|odt|all` | Обрабатывать только указанный формат      |
| `--author NAME`     | Принудительно установить автора                       |
| `--toc / --no-toc`  | Добавить/убрать оглавление                            |
| `--log-level info|error` | Уровень детализации лога                        |

**Использование:**
```sh
./doc2fb2.sh -d /книги --dry-run
./doc2fb2.sh -d /книги -o /fb2 --overwrite --log-level error
```

**Настройки (conf/doc2fb2.conf):** значения по умолчанию — `TITLE_MODE` (`auto`: auto|filename|keep), `TOC` (1), `TOC_DEPTH` (3), `PANDOC_TIMEOUT` (300 с на запуск pandoc; pandoc всегда с `--sandbox`; автор не подставляется из `$USER`), `LOG_LEVEL` (`info`: info|error), `LOG_KEEP_DAYS` (10 дней хранения `doc2fb2_*.jsonl`). Ключи командной строки главнее конфига.

Лог: JSONL-файл `doc2fb2_*.jsonl`. Логи старше `LOG_KEEP_DAYS` дней (по умолчанию 10) удаляются автоматически.

### `llamactl.sh` и `llamactl_tray.py`

Управление локальным llama.cpp независимо от редакторов (Zed, VS Code и т.п.): роутер `llama-server.service` (`:8080`, пресеты `/etc/llama.cpp/models.ini`), FIM-сервер автодополнения `llama-fim.service` (`:8012`), модели в `/var/lib/llama.cpp/models`.

**`llamactl/llamactl.sh`** — консольная утилита (ссылка `~/.local/bin/llamactl` ведёт на `llamactl/llamactl.sh`). Утилита вынесена в подкаталог `llamactl/` (вместе с `llamactl_tray.py` и `llamactl_status.py`); общие `conf/llamactl.conf`, `logs/` и `state/` остаются в корне репозитория, а каталог корня задаётся переменной `REPO_DIR` (каталог выше `llamactl/`). Без аргументов в терминале открывает интерактивное меню.

| Команда | Что делает |
|---|---|
| `status [--json]` | сервисы, модели и их состояние, VRAM/RAM, процессы на GPU, сторонние `llama-server` |
| `models`, `load М`, `unload М\|all` | список моделей; загрузка с прогрессом по VRAM; выгрузка с ожиданием освобождения памяти |
| `free-vram` | выгрузить все модели и остановить FIM (освободить видеопамять, например под игру) |
| `start\|stop\|restart [server\|fim\|all]`, `logs [server\|fim] [-f] [-n N]` | сервисы (с ожиданием `/health`) и их журнал |
| `doctor` | проверка сервисов, API, файлов моделей из пресетов, сторонних `llama-server`, кешей `~/.cache/huggingface`, места на диске; код `1` — есть проблемы |
| `kill-foreign` | завершить сторонние `llama-server`/`llama serve` (например, встроенные env `llama-vscode`) |
| `preset list\|show М\|set М КЛЮЧ ЗНАЧ\|unset М КЛЮЧ\|edit` | правка пресетов: показ diff, резервная копия `models.ini.bak-*`, перечитывание роутера через `GET /models?reload=1` без перезапуска, откат при сбое; `edit` не применяет правку, если `models.ini` изменился, пока был открыт редактор (временный файл с правкой остаётся) |
| `fit М [ОКНО]` | раскладка слоёв и экспертов MoE по GPU/CPU (`llama-fit-params`) с учётом занятой VRAM |
| `add РЕПО ФАЙЛ.gguf [--name] [--mmproj] [--ctx]` | загрузка с Hugging Face на SSD с докачкой, прогрессом и проверкой sha256 (без sha256 — отказ; `--no-verify` — скачать без проверки; размер сверяется), новая секция пресета (дописывается к `models.ini` после загрузки, поэтому правки, сделанные за время загрузки, сохраняются) |
| `remove М [--delete-files]` | убрать модель из пресетов (и удалить её файлы внутри `MODELS_DIR`) |
| `bench [М]` | замер скорости генерации и обработки промпта |
| `update [--ref ТЕГ\|SHA] [--bench] [--force]` | `git fetch` исходников; без `--ref` — последний релизный тег `bNNNN` (`LLAMA_REF`); сборка с CUDA (`sm_86`, RPATH `$ORIGIN/../lib`), установка в `/opt/llama.cpp.new`, проверка, замена с сохранением прежней версии в `/opt/llama.cpp.prev`, перезапуск сервисов и автоматический откат, если они не ответили |

**Статус** (`status`, `status --json`) собирает `llamactl_status.py` — только стандартная библиотека Python: роутер и FIM опрашиваются по HTTP, процессы, пользователи и память читаются из `/proc`, место — через `statvfs`, VRAM и процессы на GPU — напрямую из библиотеки драйвера NVML (`libnvidia-ml.so.1`, без неё — `nvidia-smi`; `LLAMACTL_NO_NVML=1` отключает NVML). Внешний процесс один — `systemctl is-active` на оба юнита. Опрос стоит ~20 мс CPU (трей опрашивает каждые 5 с). `llamactl_status.py` можно запускать и отдельно (`--conf`, `--router-url` и т.п., `--proc` — корень procfs для тестов, `-n/--dry-run` принимается — скрипт только читает).

Root-шаги (установка пресета, откат пресета, замена сборки) идут только через `sudo -A` (графическое окно пароля) root-хелпера `llamactl-root` (`ROOT_HELPER`): `install-preset`, `restore-preset`, `swap-install`; не больше одного запроса пароля на действие. Хелпер ставит `check_mytasks.sh` копией `llamactl/llamactl-root.sh` (root:root) в `/usr/local/lib/mytasks/llamactl-root`; файлы пользователя он читает с его правами, из сборки копирует только `bin/` и `lib/`. Пути — зашитые или из `/etc/mytasks/llamactl-root.conf` (root-конфиг, не выполняется). После обновления запустите `check_mytasks.sh` и согласитесь обновить root-копии; до этого `llamactl` откажет в root-шагах с подсказкой.

**Параллельные правки пресетов.** Все записи `models.ini` (`add`, `remove`, `preset set/unset/edit`, в том числе из меню и трея) идут под эксклюзивной блокировкой `flock` на `PRESET_LOCK_FILE`: новая версия файла строится из текущего содержимого и устанавливается внутри одной блокировки, второй вызов ждёт до `PRESET_LOCK_TIMEOUT_SECS` (600 с). `add` берёт блокировку только после загрузки модели, поэтому `preset set` во время многоминутной загрузки не ждёт и не теряется. В dry-run блокировка не берётся.

**Режим dry-run:** `-n, --dry-run` (до имени команды; `--dry-run` — в любом месте) — статус, проверки, `diff` пресета и сведения с Hugging Face/`git ls-remote` получаются как обычно, но ничего не загружается/выгружается, не скачивается, не правится и не перезапускается: печатаются строки `[dry-run] будет: …`, в лог пишутся события `dry_<event>`.

**`llamactl_tray.py`** — иконка в трее KDE (Python с PyQt6, шебанг `/usr/bin/env python3`; если у найденного `python3` нет PyQt6, например активен venv, трей перезапускается системным `/usr/bin/python3`), обёртка над `llamactl.sh`: статус каждые 5 с получает модулем `llamactl_status.py` в фоновом потоке, не запуская `llamactl.sh`; цвет — серый (остановлен), синий (ожидает), жёлтый (загрузка), зелёный (модель загружена), оранжевый (проблемы: FIM не работает, сторонние `llama-server`); подсказка — модель, VRAM, свободная RAM. Меню: модели (загрузить/выгрузить), освободить VRAM, сервисы, логи, проверка, пресеты (редактор, fit, замер), добавление модели с Hugging Face, обновление llama.cpp, консольное меню. Быстрые действия — в фоне с уведомлением, долгие и интерактивные — в терминале (`konsole --hold -e`, переопределяется `--terminal` или `LLAMACTL_TERMINAL`). Щелчок по иконке открывает веб-чат роутера. Автозапуск — `~/.config/autostart/llamactl-tray.desktop` (шаблон `systemd/autostart/llamactl-tray.desktop`, в нём `Exec=@MYTASKS_DIR@/llamactl/llamactl_tray.py`; его и ссылки `~/.local/bin/llamactl`, `~/.local/bin/llamactl-tray` создаёт `check_mytasks.sh`, если есть каталог установки llama.cpp), пункт меню — `~/.local/share/applications/llamactl-tray.desktop`. `--dry-run` передаёт режим всем действиям; `--print-menu [--status-file F]` печатает состояние и меню без графики.

**Конфигурация:** `conf/llamactl.conf` (пример — `conf/llamactl.conf.example`): адреса роутера и FIM, юниты и пользователь сервисов, пути пресетов, моделей, установки и исходников, архитектура CUDA, число потоков сборки, модель для замера, тайм-ауты, команда `sudo`, файл и тайм-аут блокировки пресетов (`PRESET_LOCK_FILE`, `PRESET_LOCK_TIMEOUT_SECS`), путь root-хелпера (`ROOT_HELPER`, по умолчанию `/usr/local/lib/mytasks/llamactl-root`) и что ставит `update` без `--ref` (`LLAMA_REF`, по умолчанию `latest-tag`).

**Использование:**
```sh
llamactl                         # интерактивное меню
llamactl status
llamactl load qwen3.6-35b-a3b
llamactl free-vram
llamactl -n preset set qwen3.5-9b ctx-size 49152   # сначала план
llamactl preset set qwen3.5-9b ctx-size 49152
llamactl add unsloth/Qwen3.5-4B-GGUF Qwen3.5-4B-Q4_K_M.gguf --mmproj mmproj-F16.gguf
```

### `music_downloader.sh`

Обёртка для запуска Python-проекта `music_downloader`.

**Порядок работы:**
1. Активирует виртуальное окружение (`venv`) в папке `music_downloader/`, если оно существует.
2. Запускает `music_downloader.py` и сохраняет его код выхода.
3. Деактивирует venv; при коде выхода загрузчика `0` запускает `split_by_dash.sh`, если он найден; при коде 2 (остановка по лимиту места или ошибка настроек) сортировщик тоже запускается, в лог — WARN `downloader_stopped`.
4. Логирует результат и возвращает код выхода загрузчика.

**Настройки обёртки (conf/music_downloader.conf, образец `conf/music_downloader.conf.example`):** `PYTHON_BIN` (python3), `VENV_PATH` (по умолчанию `music_downloader/venv`), `CRON_LOG` (по умолчанию `logs/cron_execution.log`). Настройки самого загрузчика — `music_downloader/music_downloader.json`.

**Конфигурация загрузчика:** в `music_downloader/music_downloader.json` общий непустой список `download_paths` задаётся в корне JSON, рядом с `sites`. Каждый трек любого моста сохраняется во все указанные папки. `path` задаёт каталог, `max_size_mb` — лимит его общего размера (по умолчанию 1024 МБ), а не квоту отдельного сайта. При переходе со старого формата перенесите общий список из сайта в корень JSON и удалите копии из `sites`: локальные настройки папок мостов больше не используются.

Папки и лимиты проверяются до обращения к сайтам и перед сохранением каждого трека. Размер проверяется в байтах, в том числе для каждого блока потока без `Content-Length`. Если трек не помещается хотя бы в одну папку, загрузчик удаляет его незавершённые `.part`, не записывает его в БД и завершает работу с кодом `2`, без запуска сортировщика. Уже сохранённые треки остаются. Контроль рассчитан на один процесс загрузчика; параллельные записи других программ требуют квот файловой системы. Отсутствующий/пустой глобальный список, отсутствующая папка или уже достигнутый лимит также завершают запуск с кодом `2`. Ошибки отдельных сайтов и треков логируются, но не обязательно меняют итоговый код выхода. При отсутствии файла конфигурации текущий загрузчик возвращает `0` без скачивания — подготовьте JSON до запуска обёртки. Пути сортировщика настраиваются отдельно.

Jamendo для категории `/` использует официальный API последних треков вместо HTML главной страницы, выбирая только записи с разрешённым скачиванием. Пустые результаты и ошибки явно логируются; подробности — в README загрузчика.

Мосты `shazam_com` (мировой Top 200; аудио ищется по точному совпадению в общем списке `search_sources`), `beufm_kz` (текущий эфирный трек радио Beu FM и готовые записи эфира; аудио ищется так же, а песни, которых нет нигде, записываются из эфира службой `beufm-recorder.service` — лучший из трёх выходов в эфир, см. `music_downloader/README.md`) и `mychords_net` (новинки, аудио из встроенного плеера xpleer, без плеера — в `search_sources`) получают ссылку на файл только перед скачиванием нового трека (`resolve_track`), поэтому уже скачанные позиции не вызывают лишних запросов.

Перед сохранением движок чистит теги ID3 скачанного MP3 (`mutagen`): в названии, исполнителе, альбоме и других полях остаются только данные о песне, ссылки на сайты и служебные кадры (URL-кадры, кодировщик, Windows Media, реклама в copyright/издателе/TXXX) переносятся в один оптимизированный комментарий без повторов; MusicBrainz, ReplayGain, ISRC и прочие данные релиза сохраняются. Правила — в разделе «Очистка тегов ID3» README загрузчика.

**Логи:** в общей папке `logs/` обёртка пишет `music_downloader-<timestamp>.jsonl` (оставляет последние 10 файлов), Python-движок — `music_downloader_engine-<timestamp>.jsonl` (очистка по глобальным `log_cleanup_days` и `log_max_files`, по умолчанию 10 дней и 10 файлов). Текстовый вывод загрузчика и сортировщика записывается в `logs/cron_execution.log`.

**Использование:**
```sh
./music_downloader.sh
```

> Подробнее — в [README загрузчика](music_downloader/README.md). Каталог `music_downloader/` входит в этот репозиторий как обычная папка, без вложенного `.git` и без submodule. Код, драйверы, тесты и шаблон конфигурации версионируются вместе с `mytasks`; рабочий JSON, БД, логи и `venv` исключены правилами `music_downloader/.gitignore`. CI загрузчика находится в `.github/workflows/music-downloader.yml`.

**Режим dry-run:** `-n, --dry-run` — загрузчик `music_downloader.py` не запускается (venv не активируется), `cron_execution.log` не пишется; сортировщик запускается с `--dry-run` и показывает свой план.

### `sources.sh`

Синхронизация файлов на основе конфиг-файла `conf/sources.conf` с помощью `rsync`, а также архивация каталогов в `7z`.

**Формат конфига** (каждая строка):
```
источник | назначение | rsync-аргументы
7z | каталог | каталог_архивов | сколько_хранить | опции_7z
```

Строка, начинающаяся с `7z`, создаёт архив `<имя каталога>-ГГГГ-ММ-ДД.7z` в `каталог_архивов` (оба пути задаются в конфиге). Перед добавлением строки оценить размер каталога (`du -sh`) и место в каталоге архивов с учётом числа хранимых копий: медиа почти не сжимаются, а архив создаётся заново каждую ночь. Архив пишется во временный `.part` и переименовывается только после успеха; повторный запуск в тот же день заменяет архив за сегодня. `сколько_хранить` — число последних архивов этого каталога (`0` — старые не удаляются, пустое поле — `SEVENZIP_KEEP`, по умолчанию `3`); остальные удаляются после успешной архивации. Пустые `опции_7z` заменяются на `SEVENZIP_DEFAULT_OPTS` (`-t7z -mx=5 -snl`: симлинки хранятся ссылками); исключения — `-xr!.cache`. Код возврата 7z `1` (файл изменился во время чтения) считается предупреждением, `2` и выше — ошибкой (`.part` удаляется, старые архивы не трогаются). Настройки задаются строками `ИМЯ=значение` в `conf/sources.conf` (без пробелов вокруг `=`, файл не выполняется как shell, в примере они закомментированы) и главнее окружения: `SEVENZIP_BIN` (7z), `SEVENZIP_DEFAULT_OPTS` (`-t7z -mx=5 -snl`), `SEVENZIP_KEEP` (3), `LOG_KEEP_DAYS` (10).

**Опции:**

| Опция | Описание                                          |
|-------|---------------------------------------------------|
| `-c`  | Указать альтернативный конфиг                     |
| `-n`  | Режим dry-run (передаёт `--dry-run` в rsync; для `7z`-строк печатает план архивации и удаления старых архивов) |
| `-E`  | Разобрать кавычки в аргументах rsync через `xargs`, без выполнения `eval` |
| `-h`  | Справка                                           |

**Логи:** JSONL-файл `logs/sources_YYYY-MM-DD-report.jsonl`. Логи старше `LOG_KEEP_DAYS` дней (по умолчанию 10) удаляются автоматически. Все строковые поля, включая пути, экранируются для JSON (табуляция, перевод строки, управляющие символы), поэтому каждая строка читается `jq`.

**Использование:**
```sh
./sources.sh
./sources.sh -n
./sources.sh -c /path/to/my.conf
```

**Расписание:** пользовательский таймер `systemd/user/sources.timer` (ставит `check_mytasks.sh`), а не cron: cron не догоняет запуск, пропущенный при выключенном компьютере, а компьютер часто выключают раньше, чем `sources.sh` с архивом 7z успевает закончить (~2,5 ч). Таймер срабатывает в 21:30, при `Persistent=true` пропущенный запуск выполняется сразу после загрузки. `sources.service` сначала ждёт, пока не закончится `music_downloader.sh`/`music_downloader.py` (не дольше 3 ч), затем запускает скрипт под `systemd-inhibit --what=shutdown:sleep --mode=block`: обычное выключение из KDE блокируется до конца копирования (принудительное выключение root-ом — нет). Недописанные `<имя>-ГГГГ-ММ-ДД.7z.part` прошлых запусков удаляются в начале следующего.

```sh
systemctl --user list-timers sources.timer
systemctl --user start sources.service   # внеочередной запуск
journalctl --user -u sources.service
```

### `split_by_dash.sh`

Анализ библиотеки перед слиянием папок (только чтение, статистика и кандидаты по паттернам): `python3 split_by_dash_analyze_music.py [N]` — первый шаг навыка `music-library-merge`.

Раскладывает файлы по папкам-исполнителям по шаблону `Исполнитель - Название`.

**Алгоритм:**
- Ищет ` - ` (или `–`, `—`) в имени файла
- Часть до разделителя становится именем подпапки
- Файл перемещается в эту подпапку; при конфликте имён файлов остаётся больший, при равном размере — уже лежащий (событие `name_dup_removed`)
- Файл без ` - ` в имени не пропускается молча: `artist` (иначе `album_artist`) и `title` читаются ffprobe, файл переименовывается на месте в `Исполнитель - Название.расширение` (имена по правилам Windows, пустой `title` — основа старого имени) и дальше раскладывается как обычно. События `renamed_by_tag` (в dry-run `dry_renamed_by_tag` с планом переименования и перемещения); нет ffprobe или тега исполнителя — `skip_no_artist` (WARN), файл не трогается. Теги сверяются со старым именем (ключ: транслитерация кириллицы в латиницу, нижний регистр, только `[a-z0-9]`, `y`→`i`; сравниваются первые 3 символа первого слова): artist совпал — как есть; совпал только title — они меняются местами (`tags_swapped`, INFO); не совпало ничего — `skip_tag_mismatch` (WARN); исполнитель с « - » — `skip_artist_dash` (WARN). Конфликт имён (одноимённый файл в каталоге, в папке исполнителя или в ней же в `DEST_DIR`) решает размер: остаётся больший, при равном размере удаляется новый (`tag_dup_removed`, общий с конфликтом регистра `resolve_case_files`).
- **Спорные слияния проверяются.** Если у папок группы совпадает «мягкий» ключ (без пробелов, `_`, `+`, `&`, `,`, апострофов, `!`, `?` и точек в конце слов), группа объединяется сразу. Иначе (точки между буквами, дефисы: `G.A.M.E` / `Game`, `Jay-Z` / `Jay z`, `K-Maro` / `Kmaro`) слияние сначала проверяется **по файлам**: у всех папок должен быть общий тег исполнителя (`artist`/`album_artist`, до 5 файлов на папку, нужен `ffprobe`). Если файлы не подтвердили, слияние проверяется **по официальным источникам** (при `OFFICIAL_NAMES=yes`): у всех папок (по имени и тегам) должен быть общий артист MusicBrainz (имя или псевдоним совпадает точно); тогда папка получает официальное имя артиста (`G.A.M.E` + `Game` → `The Game`). Если артисты разные или подтвердить нечем, слияние **отклоняется** (строка `Внимание: спорное слияние отклонено …`, событие `merge_rejected`). Решения кэшируются в `state/split_by_dash_verdicts.tsv` (`ключ<TAB>merge|keep<TAB>причина`); строку можно поправить вручную, чтобы принудительно объединить или не объединять группу.
- **Имена, безопасные для Windows** (файлы синхронизируются Syncthing между Linux и Windows, недопустимые там не синхронизируются). Применяется к создаваемым папкам, перемещаемым файлам и ко всем существующим записям внутри обработанных каталогов и `DEST_DIR` на любой глубине:
  - символы `< > : " \ | ? *` и управляющие заменяются на `_`;
  - `&` без пробелов с обеих сторон получает их, и в папках, и в файлах: `10AGE&Анет Сай` → `10AGE & Анет Сай`, `Kaskade&BUNT - Song.mp3` → `Kaskade & BUNT - Song.mp3`, `A&B&C` → `A & B & C` (если пробел есть хотя бы с одной стороны, имя не меняется);
  - ведущие пробелы, конечные точки и пробелы удаляются: папка `Автор.`, часть `Автор.` в `Автор. - песня.mp3.` и конечная точка после `mp3` (при раскладке файла из корня) → `Автор/Автор - песня.mp3`; `Fred again..` → `Fred again`;
  - зарезервированные имена `CON`, `PRN`, `AUX`, `NUL`, `COM1-9`, `LPT1-9` (любой регистр, любое расширение) получают префикс `_` (`CON.mp3` → `_CON.mp3`);
  - переименованная папка, совпавшая с существующей без учёта регистра, объединяется с ней; файл при **точном** совпадении имени: при конфликте имён файлов остаётся больший, при равном размере — уже лежащий (событие `name_dup_removed`);
  - файлы в одном каталоге, различающиеся только регистром имени (Windows хранит только один из них): **остаётся больший по размеру**, меньшие удаляются (при равном размере остаётся первый по кодовым точкам, заглавные раньше строчных); каждое удаление пишется в лог событием `case_dup_removed` с размерами, в dry-run — строкой `[dry-run] будет: Удалён файл меньшего размера…`. Папки глубже первого уровня, различающиеся только регистром, лишь выводятся строкой `Внимание: …` и записью `case_collision` (содержимое автоматически не объединяется);
  - ограничения длины отдельно не применяются: лимит Linux (255 байт) строже лимита Windows (255 символов UTF-16).
  - **исключения:** имена из `conf/split_by_dash.keep.conf` (точное совпадение имени файла или папки, по одному на строку, `#` — комментарий; образец — `conf/split_by_dash.keep.conf.example`) скрипт не переименовывает вообще, например `VashKevich&Olisha - Вызывай скорую.mp3`.
  Существующие имена файлов вида `Автор. - песня.mp3` внутри папок не переименовываются (точка в середине имени допустима в Windows).
- Папки, различающиеся только регистром, знаками, пробелами, `&`, апострофами и подчёркиваниями (в том числе `Имя Фамилия` с пробелами и кириллицей), объединяются, причём каждый каталог обрабатывается независимо: сравниваются только прямые подпапки внутри одного каталога, вложенные папки (альбомы внутри исполнителя) и другие каталоги (например, `Music` при обработке `_cloud`) не учитываются. Ключ сравнения — нижний регистр и только буквы/цифры (как `normalize_db_text` в `music_downloader`): `10AGE Анет Сай` = `10AGE&Анет Сай`, `Ағайындылар тобы & Айгерім Битанова` = `Ағайындылар Тобы Айгерім Битанова`, `Банд'Эрос` = `Банд\`Эрос` = `БандЭрос`, `Dua_Lipa_` = `Dua Lipa`. Порядок слов не учитывается, поэтому `A & B` и `B & A` — разные папки. Эталон выбирается так:
  - для файла `Исполнитель - Название` в корне — папка с регистром исполнителя из имени файла (нет — создаётся), затем общий проход ниже;
  - **официальное имя** (если `OFFICIAL_NAMES=yes`): из MusicBrainz (`musicbrainz.org/ws/2/artist`, с паузой `OFFICIAL_DELAY` (1 с)) принимается артист с оценкой ≥ `OFFICIAL_MIN_SCORE` (90), чьё официальное имя даёт тот же ключ (например, `Банд’Эрос` с типографским апострофом, `ABBA`, `AC/DC` → `AC_DC`); папка создаётся, даже если среди вариантов её нет. Результаты и отрицательные ответы кэшируются в `state/split_by_dash_official.tsv` (`ключ<TAB>имя`, `-` = не найдено; файл можно править вручную, чтобы задать имя самому); при сетевой ошибке в кэш ничего не пишется. Нужны `curl` и `jq`. Для коллабораций (`A & B`) в MusicBrainz записей нет — работает правило ниже;
  - иначе лучший из существующих вариантов, по порядку: 1) не «КАПСОМ» целиком (`HURTS` проигрывает `Hurts`); 2) без `_`/`+` (следы замены знаков: `Dua_Lipa_` проигрывает `Dua Lipa`); 3) **приоритет `&`**: ` & ` → `&` → `, ` → прочее; 4) больше файлов; 5) ближе к «Первая заглавная, остальные строчные»; 6) первая по кодовым точкам.

  Содержимое остальных папок переносится в эталонную (для файлов при конфликте имён остаётся больший, при равном размере — уже лежащий (событие `name_dup_removed`); для папок — суффикс `.1`, `.2`…), остальные папки удаляются. Регистр и знаки сравниваются через `awk` в UTF-8 (нужен gawk; NFKC-нормализации нет). Перенос в `DEST_DIR` сливает только папки с точно совпадающим именем; нечёткое слияние `DEST_DIR` выполняется отдельным проходом после переноса. Режим `--dry-run` тоже обращается к MusicBrainz и пишет кэш (`state/`), но папки и файлы не меняет.
- Необязательные ключи `conf/split_by_dash.conf` (`КЛЮЧ=значение`, главнее окружения): `OFFICIAL_API` (адрес MusicBrainz), `OFFICIAL_UA` (User-Agent), `OFFICIAL_CACHE` (файл кэша, по умолчанию `state/split_by_dash_official.tsv`), `OFFICIAL_TIMEOUT` (20 с), `OFFICIAL_MAX_BYTES` (5 МБ — предел ответа MusicBrainz), `OFFICIAL_DELAY` (1 с), `OFFICIAL_MIN_SCORE` (90), `OFFICIAL_MAX_TRIES` (3 варианта имени на папку).

**Источники каталогов:**
1. Аргумент командной строки: `./split_by_dash.sh /путь/к/папке` (несуществующий каталог — ошибка с кодом 2, без перехода к конфигу). `DEST_DIR` из конфига при явном каталоге **не применяется**; целевой каталог задаётся ключом `--dest КАТАЛОГ`
2. Конфиг-файл `conf/split_by_dash.conf` (список папок, по одной на строку)

**Перенос результата (опционально):**
- Строка `DEST_DIR=/путь/к/каталогу` в `conf/split_by_dash.conf` задаёт каталог, куда переносятся все получившиеся папки-исполнители после разбора
- Если папки с таким именем в `DEST_DIR` ещё нет — она переносится целиком
- Если такая папка уже существует — файлы объединяются в неё (при конфликте имён файлов остаётся больший, при равном размере — уже лежащий (событие `name_dup_removed`)), а опустевший источник удаляется
- Без `DEST_DIR` папки остаются внутри исходного каталога
- Все операции переноса/объединения логируются

**Логи:** JSONL-файл в `logs/`. Хранятся 10 последних файлов.

**Опции:**

| Опция | Описание |
|-------|----------|
| `-n, --dry-run` | Только показать план (создание папок, перемещение файлов, объединение папок разного регистра, перенос в `DEST_DIR`) строками `[dry-run] будет: …`; файловая система не меняется. В лог те же действия пишутся событиями `dry_<event>`. Для папок, которые в плане ещё не созданы, содержимое при переносе в `DEST_DIR` не перечисляется — файлы видны в строках раскладки |
| `--dest КАТАЛОГ` | Целевой каталог результата при запуске с явным каталогом (`DEST_DIR` из конфига действует только в режиме по списку из конфига) |
| `-h, --help` | Справка |

**Использование:**
```sh
./split_by_dash.sh /path/to/music
./split_by_dash.sh --dry-run /path/to/music
./split_by_dash.sh   # использует conf/split_by_dash.conf
./split_by_dash.sh -n   # проверка по конфигу без изменений
```

### `unpack-fb2zip.sh`

Распаковывает архивы `*.fb2.zip`, извлекая `.fb2`-файлы в тот же каталог.

**Возможности:**
- Рекурсивный поиск `*.fb2.zip`
- Конфликты имён разрешаются суффиксами `_1`, `_2`…
- Имя записи передаётся `unzip` без шаблонов; размер записи ограничен `--max-mb` (200 МБ, или `UNPACK_FB2ZIP_MAX_MB`)
- Режим `--dry-run`
- JSONL-логирование

**Опции:**

| Опция              | Описание                                          |
|--------------------|---------------------------------------------------|
| `-p, --path DIR`   | Корневая папка для поиска (обязательно)           |
| `--dry-run`        | Только показать действия                          |
| `--log FILE`       | Путь к JSONL-логу                                 |
| `-h, --help`       | Справка                                           |

**Использование:**
```sh
./unpack-fb2zip.sh -p /книги
./unpack-fb2zip.sh -p /книги --dry-run
```

### `utility_bills.sh`

Квитанции ЖКУ: заходит в почтовый ящик (IMAP, только чтение), в указанной папке ищет письма с
указанных отправителей (`search.from` — массив email), скачивает PDF-квитанции «Единый платёжный документ» Астана ЕРЦ, распознаёт их
(страница — картинка без текста: `pdfimages` + `tesseract` по ячейкам таблицы) и записывает все
данные — шапку, каждую услугу, показания, тарифы по ступеням, суммы и результаты проверок — в
SQLite `utility_bills/utility_bills.db` с представлениями для отчётов и графиков. PDF хранится в
базе как BLOB, рядом сохраняются метаданные исходного файла и письма. Обработанные письма
запоминаются и при следующих запусках пропускаются. Выполняются сверки строк, тарифов и «Итого»;
результаты проверки могут потребовать ручного просмотра.

```bash
./utility_bills.sh --check            # конфигурация, tesseract (rus, kaz, eng), pdfimages
./utility_bills.sh --dry-run          # план: что будет скачано и записано; ничего не меняет
./utility_bills.sh                    # почта → PDF → БД
./utility_bills.sh --file ~/A000123456-2026-*.PDF   # импорт уже скачанных квитанций
```

**Настройки:** обёртка — `conf/utility_bills.conf` (`PYTHON_BIN`, `VENV_PATH`, `CRON_LOG`),
программа — `utility_bills/utility_bills.json` (ящик, папка, отправители, БД, OCR, ступени
тарифа). **Расписание:** `systemd/user/utility-bills.timer` — 20-го числа в 10:00,
`Persistent=true` (ставит `check_mytasks.sh`). **Логи:** `logs/utility_bills-*.jsonl` (обёртка),
`logs/utility_bills_engine-*.jsonl` (программа), вывод — `logs/cron_execution.log`; в `--dry-run`
план печатается в терминал. Подробно — [README проекта](utility_bills/README.md), CI —
`.github/workflows/utility-bills.yml`.

## Тесты и статический анализ

Тесты и проверки кода локально не запускаются — только в CI GitHub Actions
после пуша; состав проверок и порядок чтения результата — в разделе
«Валидация» [`ai-md/AI.md`](ai-md/AI.md), не дублируются здесь. Инструменты
проверки на рабочую машину не ставятся: `pytest` и `ruff` для загрузчика —
в `music_downloader/requirements-ci.txt` и `utility_bills/requirements-ci.txt`, которые использует только CI.

Кратко: `tests/` — по Bats-файлу на актуальный корневой скрипт плюс общий
`all_scripts_syntax.bats` (синтаксис каждого корневого `*.sh` и `llamactl/*.sh` по шебангу); внешние
команды стабируются через временный `PATH` (для `system_monitor.sh`
настоящими остаются `sqlite3` и `jq`). CI — независимые workflow:
`.github/workflows/bats-tests.yml` (все Bats-тесты на каждый push/PR),
`.github/workflows/shellcheck.yml` (ShellCheck `error`+`style`+`-o all`, Ruff трея и статуса `llamactl`, синтаксис
`bash -n`/`sh -n`, сканер небракетированных `$VAR`, `py_compile` (корневые `*.sh`/`*.py` и `llamactl/*.sh`/`llamactl/*.py`) — только
при изменении `*.sh`/`*.py`), `.github/workflows/music-downloader.yml` (Ruff и
pytest загрузчика на Python 3.14), `.github/workflows/utility-bills.yml` (Ruff и pytest `utility_bills/`) и `.github/workflows/security-scan.yml`
(Semgrep, Trivy, OSV-Scanner, Gitleaks, CodeQL; еженедельно и на push/PR).

Версии инструментов CI закреплены: `shellcheck-py==0.11.0.1` из PyPI (ставится через `pipx`), `semgrep==1.183.0`,
bats-core — тег `v1.11.1`; ruff в `shellcheck.yml` (для `llamactl`) — `ruff==0.17.0`, в `requirements-ci.txt`
загрузчика — `ruff>=0.17.0`, у `utility_bills` — `>=0.17.0,<0.18`. У всех workflows на верхнем уровне
`permissions: contents: read`. Workflow `music-downloader.yml` запускает и `tests/test_mht_to_fb2.py`.
