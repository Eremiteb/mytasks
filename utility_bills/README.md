# utility_bills — квитанции ЖКУ из почты в SQLite

Программа заходит в почтовый ящик (IMAP), в указанной папке ищет письма от указанных отправителей,
скачивает PDF-квитанции «Единый платёжный документ» Астана ЕРЦ, распознаёт их и записывает все
данные по коммунальным платежам в базу SQLite — для отчётов, графиков и анализа.

Запуск — обёртка [`utility_bills.sh`](../utility_bills.sh) в корне mytasks; расписание —
пользовательский таймер `systemd/user/utility-bills.timer`: **20-го числа каждого месяца в 10:00**
(`Persistent=true`: если компьютер был выключен, запуск выполняется после загрузки). Таймер ставит
`check_mytasks.sh`.

## Как работает

1. **Почта.** Сначала программа получает **полный список** писем папки от
   отправителей из массива `search.from` (без ограничения числом дней) и печатает его с
   пометками «новое» / «обработано», затем обрабатывает только новые, по порядку дат. Адрес
   отправителя сравнивается как полный email без учёта регистра; в заголовке From должен быть ровно один
   адрес, а сам заголовок — один (иначе письмо не берётся); тема не учитывается. Тема и отправитель печатаются без управляющих и bidi-символов
   и не длиннее 200 символов.
2. **Обработанные письма пропускаются.** Каждое обработанное письмо записывается в таблицу
   `messages` (ключ — `Message-ID`, если его нет — `uid:<папка>:<UIDVALIDITY>:<UID>`); при следующих
   запусках такие письма не скачиваются. Письмо, PDF из которого не удалось разобрать, обработанным
   **не** помечается и повторяется в следующий раз. Письмо без PDF помечается со статусом `no_pdf`.
   Письмо больше лимита (`RFC822.SIZE` > `max_attachment_mb` × 4/3 + 1 МиБ — запас на base64 и текст)
   не скачивается: предупреждение `message_too_large` и статус `too_large` (в dry-run — только план);
   чтобы после увеличения лимита письмо скачалось, удалите его строку из `messages`. Письмо, для которого
   сервер не вернул `RFC822.SIZE`, не скачивается: предупреждение `message_size_unknown`, статус не ставится,
   письмо повторится при следующем запуске.
   Сбой одного письма или PDF (ошибка IMAP при получении, БД, диска, непредвиденная ошибка разбора —
   событие `parse_crashed`/`pdf_failed`) пишется в лог, остальные письма обрабатываются.
3. **PDF** хранится только в базе (`bills.pdf`), отдельного архива файлов нет: на время разбора он пишется
   во временный каталог (права 700) и удаляется. PDF, который уже есть в базе (по SHA-256), не
   разбирается повторно.
4. **Распознавание.** В квитанции ЕРЦ нет текстового слоя — страница целиком картинка. Поэтому:
   растр извлекается `pdfimages` (poppler) → в нём находятся линии таблицы (12 колонок по строке
   заголовка; объединённые ячейки — по отсутствию вертикальной линии в строке) → каждая ячейка
   распознаётся `tesseract` отдельно. Ячейка делится на подъячейки: сначала по внутренним вертикальным
   линиям («17 | 2»), затем каждая часть — по горизонтальным. Подъячейки под горизонтальной линией —
   отдельная строка услуги (`sub_row = 1`): у электроэнергии Астана-РЭК это «Шығындар/потери»; она
   записывается всегда, даже пустая, потому что в квитанции это отдельная строка. Числовые колонки читаются только цифрами на трёх масштабах
   (`ocr.cell_scales`), значение выбирается голосованием. Денежные суммы читаются через `money_numbers`:
   запись без точки из трёх и более цифр («7746») — потерянная точка, значение делится на 100 (77.46);
   «4572.00» и «12» остаются как есть. Тарифная ячейка распознаётся при каждой ширине стирания линий из
   `ocr.tariff_line_erase_px`. В `raw` строки для каждой колонки сохраняется `<колонка>~ocr` — список
   подъячеек (рамка, текст, числовой ли проход, масштаб, ширина стирания). Дата сальдо и месяц начислений берутся из
   заголовка таблицы по виду («ДД.ММ.ГГГГ» и «ММ.ГГГГ»), подписи не требуются. Лицевой счёт с корешка
   («Лицевой счет 0123456») дополняется нулями слева до 10 цифр. Шапка и низ листа (корешок) распознаются
   блоками.
5. **Контроль качества** (результаты пишутся в БД и в предупреждения лога):
   - каждая строка: «к оплате = max(сальдо − оплата, 0) + начислено + пеня + перерасчёт» (переплата
     не уменьшает начисление — так считает ЕРЦ). У строки с подстроками (электроэнергия + потери,
     отопление + горячая вода ГВС) сальдо, оплата и «К оплате» общие, а начислено — сумма подстрок
     (`accrued_total` в подстроке 0). Если строка не сходится, перебираются
     альтернативные прочтения ячеек (не больше 4 на денежную колонку) и берётся то, при котором она
     сходится (запись `raw.repaired`, примечание в `bills.notes`). Если так и не сошлась, причина пишется
     в предупреждение и в `raw.to_pay_mismatch`: `bill` — разница не больше 0.05 тг, а ни одно
     прочтение ячеек её не объясняет: «расхождение в самой квитанции (ни одно прочтение ячеек его не
     объясняет, вероятно округление ЕРЦ)»; иначе `ocr` — «вероятна ошибка распознавания».
     В обоих случаях квитанция уходит на сверку;
   - тариф: «начислено = кол-во × цена»; если при одной цене не сходится, берётся другое прочтение
     цены (`price_variants`), при котором сходится (`raw.tariff_repaired = [старая, новая]`, примечание
     «тариф X → Y по проверке «кол-во × цена»»); для электроэнергии Астана-РЭК используются три тарифные
     ступени. Нормативные границы задаются отдельно и масштабируются по числу жильцов (см.
     `ocr.tier_bounds*`); напечатанные или рассчитанные объёмы ступеней сами по себе границ не задают.
     Допуск учитывает, что цена и количество напечатаны с
     округлением до сотых (фактически 24.8124 тг вместо 24.81, 2.7689 Гкал вместо 2.770);
   - вся квитанция: сумма колонки «К оплате» = «Итого».
6. **Сверка.** Если что-то не сошлось (строка, тариф, «Итого», нераспознанная услуга), квитанция всё
   равно записывается в БД, но с флагом `bills.needs_review = 1`; в лог — `parse_warning` на каждое
   расхождение и `bill_needs_review` на квитанцию, счётчик — `runs.bills_review`. Для сверки всё уже в
   базе: PDF (`bills.pdf`), расхождения (`bills.warnings`), ожидаемые и распознанные суммы
   (`bill_items.expected_*`, флаги `*_check_ok`), тексты OCR каждой ячейки (`bill_items.raw`).
   Результат ручной сверки записывается в `bills.review_issue` (в чём проблема: ошибка распознавания,
   особенность начисления ЕРЦ…) и `bills.review_result` (итог: верные значения из квитанции, решение) с
   `needs_review = 0`. Эти поля переживают замену квитанции и `--reparse`; флаг снова ставится, только
   если изменились предупреждения. Неразобранный PDF в БД не пишется: ошибка —
   в логе (`parse_failed`/`parse_crashed`, ERROR), письмо повторится в следующий запуск.
7. **Запись.** Квитанция за тот же лицевой счёт и месяц заменяется новой (исправленная квитанция),
   строки и ступени тарифа — вместе с ней.

На отдельных квитанциях измерялось около 17 секунд на разбор (8 процессов tesseract). Это не
гарантирует точность OCR или успешную сверку каждой квитанции: результаты нужно оценивать по её
проверкам и предупреждениям.

## Установка

```bash
# системные программы (Arch/Garuda); Debian/Ubuntu: tesseract-ocr tesseract-ocr-rus tesseract-ocr-kaz tesseract-ocr-eng poppler-utils
sudo -A pacman -S --needed tesseract tesseract-data-rus tesseract-data-kaz tesseract-data-eng poppler
utility_bills/setup_venv.sh                                   # venv: numpy, pillow
cp utility_bills/utility_bills.json.example utility_bills/utility_bills.json
chmod 600 utility_bills/utility_bills.json                    # заполнить почту
./utility_bills.sh --check                                    # конфиг, tesseract, языки, pdfimages
./utility_bills.sh --dry-run                                  # список писем и план без изменений
```

`check_mytasks.sh` проверяет и создаёт всё это сам: зависимости `tesseract`, `pdfimages`, venv,
конфиг (мастер) и таймер.

## Конфигурация `utility_bills/utility_bills.json`

Файл не попадает в Git (`.gitignore`). Относительные пути — от каталога `utility_bills/`.

| Ключ | По умолчанию | Назначение |
|---|---|---|
| `imap.host`, `imap.port` | —, `993` | сервер IMAP: имя (`mail.example.kz`) или **частный** IP-адрес (IPv6 — без квадратных скобок: `fd00::5`), без `https://`, пути и порта; для IP сертификат не проверяется, публичный IP — ошибка конфигурации (см. «Безопасность») |
| `imap.security` | `ssl` | `ssl` (порт 993), `starttls` (обычно 143) или `none` |
| `imap.username` | — | логин (обычно адрес почты) |
| `imap.password` | — | пароль (приоритет — см. «Безопасность») |
| `imap.password_env` | `UTILITY_BILLS_IMAP_PASSWORD` | имя переменной окружения с паролем |
| `imap.folder` | `INBOX` | папка ящика; кириллица допустима («Квитанции», «Входящие/ЖКУ») |
| `imap.timeout_seconds` | `60` | тайм-аут соединения |
| `search.from` | `[]` | **обязательный** массив email отправителей квитанций, например `["info@aerc.kz"]`: письмо берётся, если в заголовке From ровно один адрес и он совпадает с одним из них целиком (без учёта регистра); не email или не массив — ошибка конфигурации |
| `search.attachment_glob` | `*.pdf` | маска имени вложения (также берутся вложения `application/pdf`) |
| `search.max_attachment_mb` | `20` | вложение (или файл `--file`) больше лимита пропускается с предупреждением; письмо, превышающее лимит (п. 2 «Как работает»), не скачивается |
| `search.require_auth` | `true` | письмо принимается, только если ваш почтовый сервер записал в `Authentication-Results` `dkim=pass` (`header.d` / `header.i`) или `spf=pass` (`smtp.mailfrom`) с доменом, совпадающим с доменом From или его родительским; иначе пропуск с предупреждением `message_auth_failed` (в нём только UID и домен); `false` отключает проверку |
| `search.authserv_id` | `""` | идентификатор вашего сервера в `Authentication-Results`, обычно имя хоста почтового сервера (например, `mail.example.kz`); заголовки с другим идентификатором игнорируются; обязателен при `require_auth = true`, иначе ошибка конфигурации (код `2`) |
| `db_path` | `utility_bills.db` | база SQLite |
| `ocr.languages` | `rus+kaz+eng` | языки tesseract |
| `ocr.cell_scales` | `[2, 1, 3]` | масштабы числовых ячеек для голосования |
| `ocr.tariff_line_erase_px` | `[1, 2]` | ширины стирания линий (px), при которых распознаётся тарифная ячейка |
| `ocr.workers` | `8` | параллельных процессов tesseract |
| `ocr.timeout_seconds` | `60` | тайм-аут одного вызова tesseract/pdfimages |
| `ocr.tier_bounds` | `[70, 140]` | верхние границы ступеней тарифа электроэнергии, кВт·ч |
| `ocr.tier_bounds_per_resident` | `true` | границы умножаются на число жильцов из шапки квитанции |
| `ocr.tier_residents_default` | `2` | число жильцов, если поле «Кол. человек» в квитанции пустое |
| `ocr.max_page_pixels` | `60000000` | наибольший растр страницы, пикселей (см. «Безопасность») |
| `ocr.max_page_images` | `20` | наибольшее число изображений на первой странице PDF |
| `ocr.max_table_rows` | `40` | наибольшее число строк таблицы услуг (в квитанции около 12) |
| `ocr.max_cell_pieces` | `8` | наибольшее число подъячеек в ячейке (в квитанции до 4) |

Тонкие параметры распознавания (`dark_threshold`, `hor_line_min`, `ver_line_min`, `cell_inset_px`,
`line_erase_px`, `cell_padding_px`, `empty_cell_pixels`, `checksum_tolerance`) тоже можно задать в
блоке `ocr`; значения по умолчанию — `DEFAULT_SETTINGS` в `bill_parser.py`. Неизвестный ключ,
неверный тип или число вне диапазона (`SETTING_RANGES` там же: например, `timeout_seconds` 1–3600,
`workers` 1–64, `cell_padding_px` 0–100) — предупреждение с допустимым диапазоном и значение по
умолчанию. Списочные параметры — непустые списки положительных чисел (каждое — в диапазоне).

Для Gmail, Yandex и Mail.ru нужен **пароль приложения** и включённый доступ по IMAP.

## Безопасность

- TLS к почте всегда с проверкой сертификата и имени хоста (`ssl.create_default_context()`);
  `imap.security = none` допускается только для `localhost` — пароль открытым текстом по сети не
  уходит. Ошибка проверки сертификата — отказ подключения, а не продолжение.
  **Исключение:** если `imap.host` — IP-адрес, соединение шифруется, но сертификат не проверяется (он
  выдан на имя, а не на адрес); при каждом подключении — предупреждение `imap_tls_unverified`. Подменивший
  адрес узел смог бы получить пароль, поэтому допустим только **частный** IP (`is_private`: 10/8,
  172.16/12, 192.168/16, `fc00::/7`, loopback) — адрес почтового сервера в частной сети (VPN), где
  подлинность сервера обеспечивает туннель. Публичный IP — ошибка конфигурации (код `2`); для сервера в
  интернете указывайте имя. Адреса CGNAT `100.64.0.0/10` частными не считаются.
- Ящик открывается только на чтение (`EXAMINE`, `BODY.PEEK`): письма не помечаются прочитанными и не
  перемещаются.
- Пароль — в `utility_bills.json` с правами `600` (заполненное поле главнее переменной) или, при пустом
  поле, в переменной `UTILITY_BILLS_IMAP_PASSWORD`, например `export …` в `conf/utility_bills.conf`; в
  логи и вывод не попадает. Конфиг с заполненным паролем, доступный другим (права шире `600`) или
  принадлежащий другому пользователю, — ошибка конфигурации (код `2`, fail closed); права проверяются
  `fstat` того же дескриптора, из которого читается файл.
- Квитанции содержат персональные данные (адрес, лицевой счёт, телефоны): БД (с PDF внутри) и её
  резервные копии создаются с правами `600`, временный каталог разбора — `700`; БД и рабочий конфиг
  исключены из Git.
- Вложения — недоверенные данные (адрес From легко подделать): имя файла очищается от путей,
  управляющих и bidi-символов, основа — не длиннее 120 символов / 180 байт (расширение сохраняется);
  размер ограничен `search.max_attachment_mb`, слишком большое письмо не скачивается; вложение считается PDF
  только по сигнатуре `%PDF-` в начале содержимого (заявленные тип и имя не учитываются); число и размер изображений страницы проверяются по `pdfimages -list` до
  извлечения и ещё раз при открытии растра (`ocr.max_page_images`; `ocr.max_page_pixels` — A4 при
  600 dpi около 35 млн пикселей); число строк
  таблицы и подъячеек ограничено (`ocr.max_table_rows`, `ocr.max_cell_pieces`), перебор вариантов
  прочтения — тоже; у `pdfimages`/`tesseract` тайм-аут.
- Логи: лицевой счёт маскируется до `***3456` (последние 4 цифры), длинные цифры в именах файлов — так же
  (`***NNNN`); логин IMAP и значения аргументов обёртки в лог не пишутся — только имена ключей (`--file`,
  `--dry-run`). `pdfimages`/`tesseract` запускаются с минимальным окружением (`PATH`, `LANG`, `LC_ALL`,
  `TESSDATA_PREFIX`), пароль IMAP им не передаётся.
- SQL только параметризованный (имена таблиц в DDL — константы кода).

## Запуск вручную

```bash
./utility_bills.sh                       # почта → PDF → БД (вывод — в logs/cron_execution.log)
./utility_bills.sh --dry-run             # план: что будет скачано и записано; ничего не меняет
./utility_bills.sh --file ~/Загрузки/A000123456-2026-*.PDF   # импорт уже скачанных PDF
./utility_bills.sh --reparse             # разобрать заново все PDF из базы (после улучшения парсера)
./utility_bills.sh --migrate-db [--dry-run]
```

`--dry-run` (`-n`) ничего не меняет — ни БД (не создаётся), ни почтовый ящик, — но
читает почту и разбирает PDF во временном каталоге, печатает план строками `[dry-run] будет: …` и
предупреждения проверок. Логи запуска (`logs/utility_bills-*.jsonl` обёртки и
`logs/utility_bills_engine-*.jsonl` программы) пишутся и в dry-run.

Коды выхода: `0` — успех, `1` (и любой другой) — были ошибки (почта, разбор PDF; событие
`engine_failed`), `2` — нет/неверная конфигурация или нет `tesseract`, его языков, `pdfimages`
(`config_error`), `3` — обёртка уже выполняется (`already_running`).

### Блокировка, umask, повтор, ограничения юнита

- Один запуск за раз: обёртка берёт `flock -n` на `utility_bills/.utility_bills.lock`; при занятой
  блокировке (таймер и ручной запуск одновременно) пишет `already_running` в JSONL-лог, сообщение в
  stderr и завершается кодом `3`, движок не вызывается. Файл блокировки в Git не попадает.
- Ресурсы юнита: `MemoryMax=1G`, `CPUQuota=200%` (OCR запускает до `ocr.workers` процессов tesseract).
- `umask 077` в `utility_bills.sh`; движок и сам ставит маску `077` (`os.umask` в `main`, прежняя
  возвращается при выходе), поэтому логи и прочие создаваемые файлы доступны только владельцу и при
  запуске без обёртки.
- Повтор: `utility-bills.service` — `Restart=on-failure`, `RestartSec=15min`,
  `RestartPreventExitStatus=2 3`, не более 4 стартов за 2 ч (после загрузки сеть/VPN может быть ещё не
  поднята); ошибки конфигурации (`2`) и занятая блокировка (`3`) не повторяются. `TimeoutStartSec=2h`.
- Хардненинг юнита (подробности — комментарии в `systemd/user/utility-bills.service`): писать можно
  только в `ReadWritePaths=` (`utility_bills`, `logs`); если `db_path` вынесен за
  каталог проекта, добавьте его туда, иначе запись будет отклонена (`Read-only file system`).

## База данных

Версия схемы — `PRAGMA user_version`; схема меняется только миграцией (`DB_SCHEMA` +
`DB_MIGRATIONS` в `utility_bills.py`, пересборка таблиц `_rebuild_table`, перед миграцией —
резервная копия `<база>.bak-v<версия>-<дата>`).

| Таблица | Содержимое |
|---|---|
| `bills` | квитанция: лицевой счёт, `period` (месяц квитанции, ГГГГ-ММ), `service_period` (месяц услуг), `saldo_date` и `accrual_month`, поля документа и плательщика, суммы и результаты проверок, предупреждения (JSON), OCR-текст шапки/таблицы/низа, версия парсера, имя/путь/SHA-256/размер файла, **исходный PDF в `pdf` (BLOB)**, путь копии для сверки, ключ и метаданные письма (`email_subject`, `email_from`, `email_date`) |
| `bill_items` | строка услуги: название (каноническое и как в квитанции), поставщик и его телефон, сальдо, оплата, предыдущее/текущее показание, расход, кол-во (+ второе число подъячейки), тариф, начислено (+ все числа ячейки), пеня, перерасчёт, к оплате, ожидаемые «к оплате» и «начислено», результаты проверок, тексты OCR каждой ячейки (`raw`, JSON) |
| `bill_item_tariffs` | ступени тарифа в квитанции: номер, применённое название (с учётом жильцов) и метка для справочника, цена, единица, границы, объём на ступени, сумма |
| `bill_formats` | наблюдаемые раскладки, сгруппированные по `signature`: описание и признаки (`features`), первый/последний период и число квитанций. Это признаки представления документа, не история тарифов. |
| `tariffs`, `quantities` | справочники тарифов и количеств с историей (ниже) |
| `messages` | обработанные письма (по ним письма пропускаются при следующих запусках): Message-ID, папка, UID, тема, отправитель, получатели, дата, размер, статус, число PDF, заголовки, текст (до 100 000 символов) и метаданные вложений (JSON: имя, тип, размер, SHA-256, взято ли в разбор) |
| `runs` | итоги запусков |

Исторические справочники `tariffs` и `quantities` (пересобираются из всех квитанций при каждой записи — верны при любом порядке
импорта, замене квитанции и `--reparse`; записи `source = 'manual'` не трогаются):

| Таблица | Одна запись | Поля |
|---|---|---|
| `tariffs` | период действия одной цены услуги (ступени) | `service`, `tier`, `tier_name` («Минимальный тариф (до 70 кВт·ч на жильца)»), `price`, `unit`, `valid_from`…`valid_to`, `is_current`, `bills_count`, `first_bill_id`/`last_bill_id`, `provider`, `source` |
| `quantities` | период неизменного значения колонки «Кол-во» | `service`, `kind` (`quantity` — основное число, `quantity_extra` — второе число подъячейки), `value`, `unit` (м², м³, кВт·ч из тарифа), `normative` (1 — площадь, число человек; 0 — объём по счётчику или расчётный, например ОДН), те же поля периода |

Месяцы — месяцы оказания услуг. Период разрывается, если значение сменилось или пропало в месяце, за
который квитанция есть; месяц без квитанции в базе не разрывает период. При импорте в лог пишутся
события `tariff_changed` («Тариф изменился: … 20.37 → 24.81 с 2026-07») и `quantity_changed` (только
нормативные количества: площадь, число человек). При импорте архива вразнобой сообщение отражает то, что
известно на момент импорта; итоговый справочник от порядка не зависит.

Представления для отчётов: `v_tariffs_current`, `v_quantities_current` (действующие значения), `v_items` (плоская таблица квитанция + услуга + фактическая цена
`effective_price` = начислено / кол-во), `v_monthly` (итоги по месяцам), `v_tariffs` (история
тарифов по ступеням), `v_consumption` (показания и расход счётчиков).

```sql
-- Начисления по услугам за год (для графика)
SELECT service_period, service, accrued FROM v_items WHERE service_period LIKE '2026-%' ORDER BY 1, 2;
-- Расход электроэнергии и воды по месяцам
SELECT service_period, service, consumption FROM v_consumption ORDER BY 1, 2;
-- История тарифов и нормативов
SELECT service, tier_name, price, valid_from, valid_to FROM tariffs ORDER BY service, tier, valid_from;
SELECT service, value, unit, valid_from, valid_to FROM quantities WHERE normative = 1 ORDER BY service, valid_from;
-- Квитанции с несошедшимися проверками
SELECT period, warnings FROM bills WHERE needs_review = 1;
-- Итог ручной сверки (снимает флаг)
UPDATE bills SET needs_review = 0, review_issue = 'ошибка распознавания: …', review_result = 'в квитанции …'
  WHERE account = '0000123456' AND period = '2026-02';
```
