# AI.md

Единый источник общих и проектных требований для всех ИИ-ассистентов. Глобальные и проектные файлы `.cursorrules`, `AGENTS.md`, `CLAUDE.md`, `GEMINI.md` и `.github/copilot-instructions.md` — только точки входа со ссылкой сюда. Общие правила действуют во всех проектах; разделы о mytasks — только в mytasks.

## Применение и сопровождение

- Каждый агент самостоятельно выбирает нативные инструменты и способ выполнения требований этого файла с учётом своей платформы. Обязательны результат, ограничения и проверки; не нужно механически повторять реализацию другого агента.
- Новые и изменённые требования к агентам записывать только сюда. После однократного сокращения файлов агентов до ссылок больше не дописывать в них правила; при поломке точки входа восстанавливать только ссылку. Установщик не должен возвращать в них скопированные разделы.
- Каждый запрошенный пользователем навык и хук, включая будущие, регистрировать здесь: назначение, источник, поддерживаемые платформы и способ установки. Для навыка или хука, которым управляет проект, обновлять источник в `agent-skills/`, `install_agent_skills.sh`, нужные тесты и README; внешний пакет ставить штатным механизмом из доверенного источника без копии в публичный репозиторий. Для несовместимой платформы выбрать нативный эквивалент либо сообщить об ограничении; не копировать чужой хук слепо.
- Сейчас через `install_agent_skills.sh` распространяются навыки `model-routing`, `best-practices`, `infosec` и два поведения хуков для Claude Code, Codex и Gemini CLI: проверка меток модели в плане и напоминание перед запросом. Источники и хосты описаны ниже. Другие имеющиеся пользовательские навыки — `graphify`, `music-library-merge`, `perplexity-web-research`, `ponytail`, `security-best-practices` — устанавливаются штатным механизмом соответствующей платформы из доверенного источника, без копирования их файлов в публичный репозиторий. Здесь фиксируются обязательные условия их применения; при запросе нового навыка или хука агент добавляет его в этот реестр и обеспечивает штатную установку на поддерживаемых платформах.
- На этой машине общий пользовательский каталог навыков Codex/Gemini — `~/.agents/skills`, отдельные каталоги — `~/.codex/skills`, `~/.gemini/skills` и `~/.claude/skills`. Проверять наличие всех перечисленных навыков на каждой поддерживаемой платформе; отсутствующие устанавливать штатно из уже доверенного источника, сохраняя ресурсы навыка целиком. Для других устройств повторять это после доставки `AI.md`; содержимое внешних пакетов не включать в публичный Git.

## Общие требования для всех проектов

### Язык, контекст и ресурсы

- Общаться и задавать вопросы по-русски; идентификаторы, команды и пути не переводить. Сначала использовать память и граф проекта, затем точечный поиск `rg`. Читать только относящиеся к задаче справки и не подключать лишние инструменты.
- Во время длительной работы показывать все этапы, долю завершённой задачи, текущий этап, скорость и остаток времени, когда они измеримы; сообщать об изменениях примерно раз в 30–60 секунд без повторяющихся отсчётов. Не отключать штатный индикатор заполненности контекста. В интерфейсе без него сообщать его состояние в таких отчётах и заранее предупреждать о лимите.
- Перед значимым выбором модели, библиотеки или настройки заново сверять реальные CPU, GPU, память, диск, ОС, версии и занятость ресурсов. Новые технологии сравнивать с текущими на этом оборудовании и рекомендовать переход лишь при подтверждённом выигрыше.

### Модель и навыки

- Каждому агенту применять `model-routing` в начале каждого запроса, даже когда переключение не требуется. Claude Code использует метки `[Haiku]`/`[Opus]` для своего хука, Gemini сверяет каталог своей платформы. Перед планом или делегированием сверять актуальный каталог. Для Codex: `gpt-6-astra` — сложные решения и итоговая проверка, `gpt-6-sol` — рабочая старшая, `gpt-6-luna` — безопасная рутина; идентификаторы не считать постоянными. При доступном делегировании старшая модель планирует самостоятельную рутину для Luna. Шаги плана помечать реально выбранной моделью; короткое исключение с общим контекстом объяснять.
- Для задач с кодом и конфигурацией применять `best-practices` и `infosec`. `perplexity-web-research` применять только по прямому запросу или для независимой проверки актуальных внешних данных; перед вызовом проверять непустой `LLM_PERPLEXITY_KEY`, экспортировать только эту переменную из локального конфигурационного файла, не раскрывать её значение; актуальные модели узнавать через `perplexity --list-models`.
- `graphify` применять к вопросам о связях и содержимом кодовой базы; `music-library-merge` — при работе с музыкальной библиотекой и её скриптами; `ponytail` — в задачах с кодом для минимального полного решения. `security-best-practices` применять при явном запросе проверки или рекомендаций по безопасности для поддерживаемых языков; автоматические требования ИБ остаются за `infosec`.

### Доступ и безопасность

- Локальный root-шаг выполнять через `sudo -A` с графическим askpass, который показывает целевого пользователя. Пароль не запрашивать в чате или stdin. Если askpass не работает, определить ОС и предложить подходящий пакет; продолжить после установки.
- Для SSH с паролем использовать отдельный `ssh-askpass-gui`, `SSH_ASKPASS_REQUIRE=force`, `setsid -w` и stdin из `/dev/null`. Запрос пароля должен показывать целевого `user@host`. К серверу другого проекта обращаться только по прямому указанию в текущем запросе.
- Не помещать секреты и персональные данные в Git, публичные фикстуры, команды, URL или логи; утёкший секрет ротировать. Проверять TLS и имя хоста, ограничивать недоверенный ввод, использовать параметризованный SQL, минимальные права, безопасные временные файлы и атомарную запись. Не отключать защиту и сканеры ради удобства.
- Перед необратимым изменением данных иметь резервную копию или снимок и способ отката. Действия во внешних системах ограничивать запросом и необходимыми полномочиями.

### Код, проверка и запуск

- Перед правкой выяснять первопричину и проверять связанные вызовы, точки входа, конфиги, миграции, скрипты установки и тесты. После правки синхронно обновлять затронутые шаблоны, README и служебные скрипты. Не создавать второй механизм для существующего поведения.
- Обрабатывать ошибки явно, освобождать ресурсы, валидировать аргументы и конфигурацию. На новое нетривиальное поведение добавлять тест. В Python применять типизацию и конкретные исключения; в shell — кавычки, `${VAR}`, `[[ ]]`, `case *)`. Скрипты должны проходить `shellcheck -o all`, `shellcheck -S style`, `bash -n`; SC2312 исправлять реструктуризацией, а не подавлением.
- Тесты, линтеры и синтаксические проверки кода локально не запускать: их выполняет CI. Отсутствующую проверку добавлять в workflow. После разрешённого пуша не ждать CI автоматически; по сообщению пользователя читать упавший лог и исправлять.
- Если есть `--dry-run`, сначала выполнить его с теми же аргументами и конфигом, сверить план и ошибки. Боевой запуск на реальных данных — после успешного dry-run и прямого подтверждения именно запуска; демонстрацию делать на временной копии без боевого конфига.
- Положительный ответ на выполненную работу или вопрос о коммите означает в том же шаге коммит и обычный пуш только относящихся к задаче файлов. Подтверждение другого действия не разрешает коммит; `--force` требует отдельного согласия. Обычный пуш делать по SSH; только при `Permission denied (publickey)` использовать авторизованный `gh` как временный HTTPS credential helper без изменения Git-конфига. Секреты, `.env`, дампы, кэши и `graphify-out/` не коммитить.

### Документация и другие проекты

- При изменении кода или поведения обновлять связанные рабочие конфиги без потери секретов, безопасные примеры, README и установочные или миграционные скрипты.
- Если граф проекта существует, до ручного поиска по исходникам использовать его и после изменения кода или конфигурации обновить. Если граф отсутствует либо устарел, сообщить об этом и работать по исходникам; вне mytasks новый граф создавать после согласия. `graphify-out/` не включать в Git.

Машинные адреса и диагностические сведения оставлять в приватных справках `~/.config/ai-context/`, не переносить в публичный репозиторий.

## Валидация

Тесты и проверки кода **локально не запускать** — ни на рабочей машине, ни на QNAP или сервере (глобальное правило «Тесты и проверки кода — только в CI»). Проверку выполняет GitHub Actions после пуша: правка → коммит и пуш (по правилу подтверждения). Ожидание CI не запускать (`gh run watch`, опрос, фоновые задачи): ошибки CI присылает пользователь; по его сообщению — `gh run view <id> --log-failed` → исправить и запушить снова. Если нужной проверки нет в workflow — добавить её туда, а не запускать локально.

Что проверяет CI (`.github/workflows/`, подробности — «Тесты, CI и Git» ниже):

- `bats-tests.yml` — полный набор Bats-тестов `tests/` (bats-core), на каждый push/PR; `tests/all_scripts_syntax.bats` дополнительно проверяет синтаксис каждого корневого `*.sh` и `llamactl/*.sh` по shebang.
- `shellcheck.yml` (при изменении `*.sh`/`*.py`) — `shellcheck -S error`, `shellcheck -S style` (фигурные скобки, `[[ ]]`, ветка `case *)` и другие соглашения), `shellcheck -o all` (все дополнительные проверки, в том числе SC2312), `bash -n`/`sh -n` по shebang, поиск ссылок на переменные без фигурных скобок, `python3 -m py_compile` для корневых `.py` и `llamactl/*.py`, Ruff для `llamactl/llamactl_tray.py` и `llamactl/llamactl_status.py` (`--line-length 130`).
- `music-downloader.yml` — ставит `music_downloader/requirements-ci.txt` (рабочие зависимости + `pytest`, `ruff`; в локальный venv из `requirements.txt` они не попадают), Ruff для `music_downloader/` (`music_downloader/.ruff.toml`: Python 3.14, длина строки 120) и pytest `music_downloader/tests` + `tests/test_music_downloader.py`. Тесты используют временные каталоги и подменённые HTTP-ответы; покрывают общие глобальные пути загрузки, отклонение неверных, отсутствующих и заполненных каталогов до создания скрапера, атомарную запись и дедупликацию БД. Реальное скачивание для проверки конфигурации не запускать.
- `security-scan.yml` — Semgrep, Trivy, OSV-Scanner, Gitleaks, CodeQL.

Инструменты проверки (`shellcheck`, `bats`, `pytest`, `ruff`) на рабочую машину не ставятся: `check_mytasks.sh` их не предлагает, `music_downloader/requirements.txt` их не содержит — их ставит только CI.

Dry-run скриптов (`--dry-run`) — не проверка кода, а обязательный шаг перед боевым запуском; для него действуют прежние правила.

## Graphify

Правила обязательны для агентов, входящих через `.cursorrules`, `AGENTS.md`, `CLAUDE.md`, `GEMINI.md` и `.github/copilot-instructions.md`.

- Граф проекта находится в исключённом из Git каталоге `graphify-out/`; не добавлять его принудительно.
- Перед ручным поиском по исходникам проверять `graphify-out/graph.json` и использовать Graphify для навигации и анализа связей.
- Если граф существует, на естественно-язычные вопросы о кодовой базе сначала отвечать через `graphify query "<вопрос>"`, не перестраивая граф без необходимости.
- Если графа нет, а нужен анализ кодовой базы, выполнить из корня `graphify .`.
- После изменения кода или конфигурации выполнить из корня `graphify update .`.
- Graphify не требует паролей или API-ключей. Не запрашивать их и не останавливать работу из-за отсутствия `GEMINI_API_KEY`/`GOOGLE_API_KEY`; использовать доступное локальное или агентское извлечение.

## Устройство репозитория и общие соглашения

- Это не единое приложение, а плоский набор независимых целевых Bash/Python-скриптов в корне. Они не импортируют и не вызывают друг друга, кроме запуска `split_by_dash.sh` из `music_downloader.sh` при успехе. Если просят работать «с проектом», уточнять конкретный скрипт: общей точки входа нет.
- `split_by_dash.sh`: файл без ` - ` в имени переименовывается по тегам ffprobe (`artist`/`album_artist`, `title`) в `Исполнитель - Название.ext` и раскладывается как обычно; события `renamed_by_tag` / `dry_renamed_by_tag`, без тега исполнителя или ffprobe — `skip_no_artist` (WARN), файл не трогается. Теги сверяются со старым именем (translit_key: кириллица→латиница, `[a-z0-9]`, `y`→`i`; первые 3 символа первого слова): совпал только title — перестановка (`tags_swapped`); ничего не совпало — `skip_tag_mismatch`; artist с « - » — `skip_artist_dash`; конфликт имён (одноимённый файл в каталоге, в папке исполнителя или в ней же в `DEST_DIR`) решает размер: остаётся больший, при равном размере удаляется новый (`tag_dup_removed`, общий с конфликтом регистра `resolve_case_files`). `name_from_tags` печатает имя либо `SKIP:причина:детали`, `process_directory` разбирает префикс. Переименование — паттерном `[ "${DRY_RUN}" -eq 1 ] || mv`.
- Исключение из плоской структуры — утилита llamactl: её скрипты `llamactl/llamactl.sh`, `llamactl/llamactl_tray.py` и `llamactl/llamactl_status.py` лежат в подкаталоге `llamactl/`, а общие `conf/llamactl.conf`, `logs/` и `state/` — в корне репозитория; `REPO_DIR` в скрипте — каталог выше `llamactl/`.
- Агенты обязаны строго и в полном объёме следовать проектным инструкциям и выполнять задачи автономно до полного решения, не перекладывая работу на пользователя. Если требуются повышенные привилегии (`sudo`, изменение системных файлов `/etc`, управление `systemd`), использовать наиболее подходящий для текущей операционной системы и графического окружения инструмент аутентификации для пользователя `esimych` (`pkexec`, системный Polkit agent, `kdialog`, `zenity` через `SUDO_ASKPASS` и `sudo -A` или нативные средства ОС); запрещено просить пользователя вручную запускать команды в терминале вместо автономного выполнения и запрещено запрашивать пароли в чате.
- Любые решения всегда оптимизировать под фактическую конфигурацию этой машины (Ryzen 7 5800X, RTX 3060 Ti 8 ГБ, 31 ГБ RAM, Garuda/KDE Wayland, llama-server на GPU) и подтверждать замерами; учитывать новые технологии и свежие версии (модели, форматы, движки), но переходить на них только при подтверждённом выигрыше на этом железе. Перед значимой задачей заново проверять конфигурацию и занятость VRAM/RAM.
- Корневые Bash-скрипты используют `${VAR}`, а не `$VAR`, `[[ ]]`, а не `[ ]`, и заключённые в кавычки числовые переменные в `return`/`exit` (`return "${rc}"`). Каждый `case` содержит явную ветку `*)`. Это контролируют `shellcheck -S style` и поиск переменных без скобок.
- Если пользователь указывает на пропущенное предупреждение, ошибку или регрессию, до изменений обязательно объяснить причину пропуска, определить управляющий путь кода и класс предупреждения, сформулировать одну опровергаемую локальную гипотезу и одну дешёвую проверку. Не ограничиваться первым видимым симптомом.
- Все `cleanup_logs()` используют `find … -printf '%T@|%p\n' | sort -nr | awk 'NR > N { print $2 }'` с `mapfile -t` в Bash либо конвейером `while read` в POSIX sh; не использовать `ls | tail`. Аргумент `-name` у `find` всегда полностью заключать в кавычки: `"${SCRIPT_BASE}-*.jsonl"`.
- Скрипты с `ssh`/`sshpass` задают параметры Bash-массивом `SSH_OPTS=(...)` и раскрывают как `"${SSH_OPTS[@]}"`; не хранить их в строке с word splitting.
- Стандартная структура корневого `.sh`: `SCRIPT ID / PATHS` → `HELPERS` → `ARGS` → `MAIN`; проверки зависимостей и параметров выполняются в начале, применяется `set -eu` либо `set -uo pipefail` по модели обработки ошибок конкретного скрипта. При изменении и добавлении скриптов сохранять эту структуру.
- Каждый корневой скрипт (`.sh`, `.py`) обязан иметь режим `--dry-run` (короткая форма `-n`, если не занята): ничего не меняет (файлы, каталоги, БД, сервисы, система, сеть), печатает план строками `[dry-run] будет: …` и пишет те же действия в лог событиями `dry_<event>`; чтение и проверки работают как обычно. У скриптов-мониторов режим не пишет в БД/отчёты и не шлёт уведомления. Эталон — `split_by_dash.sh` (`log_action`, `DRY_RUN`, обёртки над `mkdir`/`mv`/`rmdir`; перемещение — `[ "${DRY_RUN}" -eq 1 ] || mv …`, а не функция, иначе shellcheck `-o all` выдаёт SC2310). Новый или изменяемый скрипт без `--dry-run` не считается завершённым: добавлять режим, описание в README и bats-тест «состояние не изменилось». Режим реализован во всех корневых скриптах; служебные логи самого запуска (`logs/*.jsonl`) в dry-run допускаются.
- **Сначала dry-run (обязательно для ИИ-агентов).** Перед любым боевым запуском скрипта, который меняет данные (файлы, каталоги, БД, сервисы, систему), агент обязан сначала получить успешный `--dry-run` на тех же аргументах и конфиге (завершился без ошибок, план просмотрен: количество и состав изменений, удаления, спорные и отклонённые операции, и соответствует ожиданиям) и только после этого предлагает пользователю решение, приложив итог dry-run; без успешного dry-run решение (боевой запуск, применение исправления) не предлагается — сначала устраняется причина сбоя или расхождения. Боевой запуск — только по прямому подтверждению пользователя именно на это действие. Не запускать скрипт без `--dry-run` «для проверки» или демонстрации на боевых данных (`/mnt/copy/Music`, `/mnt/copy/Books`, бэкапы, БД); для демо — копия скрипта во временной папке без `conf/` и с `MYTASKS_LOG_DIR` вне репозитория. Если dry-run не воспроизводит ожидаемый результат, боевой запуск не выполнять и сообщить пользователю.
- Длинные имена в `/mnt/copy/Music`: обычный вид `Исполнители/Исполнители - Название.mp3` не менять. Только если имя файла в этом виде длиннее 254 байт (UTF-8), файл называется по полному названию песни без повторения исполнителей (`Название.mp3`), а исполнители остаются один раз — в имени папки через ` & `, без запятых. Решение принято 2026-10-30 для единственного такого файла (`Төреғали Төреәлі & … & Еркін Нұржанов/Алақанымнан ұшқан аққуым.mp3`, полный вид 266 байт); на эту дату других имён длиннее 254 байт в `/mnt/copy/Music` и `mobile-music` нет.
- Файлы музыкальной и книжной библиотек синхронизируются Syncthing между Linux и Windows, поэтому скрипты, создающие или переименовывающие файлы и папки, обязаны соблюдать ограничения имён Windows: запрещённые символы `< > : " \ | ? *` и управляющие, конечные точки и пробелы, зарезервированные имена `CON`/`PRN`/`AUX`/`NUL`/`COM1-9`/`LPT1-9`, конфликты имён, различающихся только регистром. Эталон — `win_safe()` в `split_by_dash.sh` (awk, нужен gawk). Там же «&» без пробелов с обеих сторон получает их (`A&B` → `A & B`) в именах папок и файлов. Для ручной проверки `split_by_dash.sh` на боевых данных сначала `-n`/`--dry-run`; `DEST_DIR` из `conf/split_by_dash.conf` при явно указанном каталоге не применяется (целевой каталог — только `--dest`), но это не отменяет dry-run перед применением к `/mnt/copy/Music`.
- **Зашитые значения — в конфигурацию.** Пути конкретной машины, имена контейнеров и пользователей, адреса и порты, тайм-ауты, паузы, пороги и сроки хранения не пишутся в код как литералы: задаются переменной `ПАРАМЕТР="${ПАРАМЕТР:-по умолчанию}"` в начале скрипта (значение переопределяет окружение или `conf/<script_name>.conf`) и описываются в `conf/<script_name>.conf.example` и README. Исключения — пути стандартов ОС (`/proc`, `/etc/os-release`), внутренние пути образов (`/var/lib/mysql/general.log`) и константы протоколов. Срок хранения логов — общий `KEEP_LOGS` из `conf/log_template.conf` (`-v keep="${KEEP_LOGS:-10}"` в `cleanup_logs`), а не число в `awk`. Пути по умолчанию для данных скрипта — `state/` рядом со скриптом, а не каталог пользователя.
- Конфигурация скрипта хранится в `conf/<script_name>.conf` и подключается как shell-файл во время выполнения. В Git находятся только `conf/*.conf.example`; реальные `conf/*.conf` игнорируются, создаются пользователем, а скрипты при первом запуске выполняют `mkdir -p conf`. Не коммитить реальные конфиги; для нового настраиваемого скрипта добавлять соответствующий `.example`.
- Логи — по одному JSON-объекту на строку в `logs/<script>-<timestamp>.jsonl` либо в фиксированном суточном файле; ротация сохраняет последние 5 или 10 файлов скрипта. Общая схема берётся из `conf/log_template.conf`, если он есть, иначе используются встроенные значения. Записи содержат ECS-поля (`@timestamp`, `log.level`, `event.action`, `service.name`, `schema.version`) для ELK/OpenSearch/Loki/Graylog/Splunk и совместимые старые поля (`script`, `event`, `msg`, `detail`, `rc`). `logs/`, `state/` и реальные `conf/*.conf` игнорируются Git как машинно-зависимые runtime-артефакты. Каталог логов можно переопределить переменной окружения `MYTASKS_LOG_DIR` (во всех корневых скриптах, `music_downloader/setup_venv.sh` и движке `music_downloader.py`); bats-тесты, запускающие скрипт прямо из репозитория, экспортируют её в `$BATS_TEST_TMPDIR/logs`, чтобы тесты не засоряли `logs/`. Тесты, копирующие скрипт во временный каталог, этого не требуют.

## Тесты, CI и Git

- `tests/` примерно один к одному соответствует корневым скриптам (`<script>.bats`) и использует bats-core. Внешние программы (`curl`, `notify-send`, `docker`, `ssh` и другие) подменяются временными исполняемыми файлами, каталог которых добавляется в начало `PATH`; образец — `tests/getip.bats`: каталог заглушек и `env PATH="$STUB_DIR:$PATH" bash -c "..."`. `tests/all_scripts_syntax.bats` автоматически проверяет каждый корневой `*.sh` и `llamactl/*.sh` через `bash -n`/`sh -n` по shebang, поэтому новые скрипты получают проверку синтаксиса без отдельной записи.
- CI состоит из независимых workflows. `.github/workflows/shellcheck.yml` запускает `shellcheck -S error`, `shellcheck -S style`, `shellcheck -o all`, синтаксическую проверку `bash -n`/`sh -n`, поиск переменных без скобок и `python3 -m py_compile` для корневых `.py` и `llamactl/*.py`; срабатывает только при изменениях `*.sh`/`*.py`. `.github/workflows/bats-tests.yml` запускает все Bats-тесты при каждом push/PR. `.github/workflows/music-downloader.yml` устанавливает зависимости загрузчика, проверяет `music_downloader/` Ruff, публикует отчёты Ruff и запускает `music_downloader/tests/` вместе с `tests/test_music_downloader.py` на Python 3.14; фильтры путей включают загрузчик, общие тесты и сам workflow.
- Версии инструментов CI закреплены: `shellcheck-py==0.11.0.1` из PyPI (`pipx`), `semgrep==1.95.0` (`security-scan.yml`), bats-core тег `v1.11.1`; ruff в `shellcheck.yml` для `llamactl` — `ruff==0.17.0`, а `requirements-ci.txt` загрузчика — `ruff>=0.17.0`, `utility_bills` — `>=0.17.0,<0.18`. У всех workflows верхний уровень `permissions: contents: read`. `music-downloader.yml` запускает `tests/test_mht_to_fb2.py` вместе с тестами загрузчика.
- `music_downloader/` — отслеживаемый Python-подпроект этого репозитория, не вложенный Git checkout и не submodule. Его исходники, драйверы, тесты, README, `.ruff.toml`, requirements и `.json.example` коммитятся вместе с `mytasks`. Реальные `music_downloader.json`, SQLite-БД и резервные копии, логи и venv остаются локальными по `.gitignore`; не добавлять их или `graphify-out/` принудительно. Резервная копия прежних вложенных Git-метаданных хранится в игнорируемом `state/music_downloader-git-backup-6394179/`, не активна и не должна попадать в Git. `newline_to_space/` остаётся отдельным локальным Python-подпроектом, исключённым из Git.

## Резервное копирование QNAP

- `cloud_backup_qnap.sh` запускается непосредственно на QNAP NAS через Entware cron/Task Scheduler без `sudo`; вход на сервер — SSH-ключ `REMOTE_SSH_KEY` (пароль `REMOTE_PASSWORD` — только если на QNAP установлен `sshpass`); вокруг копирования выполняет на `REMOTE_HOST` `docker compose down`/`up -d`. Десктопный `cloud_backup.sh` удалён (ноябрь 2026).
- На части ядер QTS вариант QNAP не может использовать `wg`/`wg-quick` (`Protocol not supported`) и поднимает туннель вручную через userspace UAPI-сокет `wireguard-go`; см. `wg_up_userspace` и `wg_conf_get`.
- Значения конфига, подставляемые в удалённые команды, проверяются по строгим шаблонам до начала работы (имена `A-Za-z0-9._-`, `REMOTE_PATH` — абсолютный путь из `A-Za-z0-9._/-`); `umask` — `022` (архивы читает `check_backups.sh` по NFS). Raw TCP (`RAW_TRANSFER_ENABLED=1`) идёт без собственного шифрования — только при доверенных пирах WireGuard; временные файлы на сервере — через `mktemp`. Подробности — `README.md`.
- **Перед любой работой с `cloud_backup_qnap.sh` обязательно прочитать `ai-md/cloud_backup_qnap.NOTES.md`.**

## `check_backups.sh`

- Проверяет каталоги из `BACKUP_DIRS` (`conf/check_backups.conf`): наличие архивов, возраст, размер, падение размера относительно предыдущего и опционально целостность; пишет JSONL-лог, при ошибке (код `1` — проблемы с бэкапами, `2` — конфигурация/зависимости) показывает уведомление через `notify-send`.
- Расписание — systemd **user** timer `systemd/user/check-backups.{service,timer}` (`OnBootSec=4min`, `OnUnitActiveSec=1d`), ставит `check_mytasks.sh` в `~/.config/systemd/user`; в service `SuccessExitStatus=1`. Установка и проверка — `systemctl --user` (из песочницы агента user-шина доступна).
- Целостность свежего архива проверяется по умолчанию (`VERIFY_INTEGRITY="yes"`) с учётом размера: тайм-аут = размер / `VERIFY_MIN_SPEED_MBPS` + `VERIFY_TIMEOUT_BASE_SECS`, `nice`/`ionice`, кэш уже проверенных архивов в `state/check_backups.verified`, откладывание для архива моложе `VERIFY_MIN_AGE_MINUTES`. Замер 2026-10-04: NFS `/mnt/store` ≈112 МБ/с (узкое место — гигабит, `zstd -t` успевает), архив ~33,5 ГБ ≈ 5 мин. Тесты, не касающиеся целостности, задают `VERIFY_INTEGRITY="no"`.
- Недописанный архив — не ошибка (`archive_writing`, INFO): последний архив моложе `WRITING_RECENT_MINUTES`, у которого за `WRITING_CHECK_SECS` растут размер/mtime или есть локальный писатель (`lsof`, режим `w`/`u`), исключается, проверяются предыдущие готовые. `cloud_backup_qnap.sh` пишет `tar.zst` сразу под финальным именем, `sources.sh` — в `*.7z.part` (маска + `PARTIAL_SUFFIXES`); растущий `.part` снимает `archive_stale` (WARN `archive_stale_writing`), архив, изменившийся за время `verify_archive`, не помечается `archive_corrupt`. Тесты подменяют `sleep` стабом, дописывающим файл, и задают `WRITING_CHECK_SECS=0`.

## `sources.sh`

- Расписание — user-таймер `systemd/user/sources.{service,timer}` (21:30, `Persistent=true`), не cron: компьютер часто выключают до 23:00, а cron пропущенный запуск не догоняет. `sources.service` ждёт окончания `music_downloader.(sh|py)` (шаблон не должен совпадать с `music_downloader/beufm_recorder.py`) и запускает скрипт под `systemd-inhibit --mode=block` (polkit разрешает блокировку и для user-служб вне сеанса, проверено 2026-10-31). В unit-файле `$` в shell-коде экранируется как `$$`.
- Строки `7z|…` архивируют каталог (через `.part`, ротация `SEVENZIP_KEEP`, по умолчанию 3); недописанные `.part` прошлых дат удаляются в начале следующего запуска. Архив 7z `esimych-docs` не делать: ~300 ГБ (из них `media` 275 ГБ почти не сжимается) пишется ~2 ч и проверяется ~50 мин по NFS, а компьютер выключают раньше; каталог и так копируется rsync в `/mnt/store` и `/mnt/copy`. `/mnt/store/backups/esimych` в `BACKUP_DIRS` не добавлять.
- Все расписания mytasks — user-таймеры systemd, cron скриптам не нужен (демон cron и пакет `cronie` в `JOBS`/`DEPS` не добавлять): `music-downloader.timer` (21:00), `sources.timer` (21:30), `btrfs-monitor.timer` (00/06/12/18), `getip.timer` (+2 мин после загрузки и каждые 30 мин), все с догоном (`Persistent=true`, кроме `getip`). Порядок — `After=`: `sources` после `music-downloader`, `check-backups` после `sources`. Вид задания `no-cron` в `check_mytasks.sh` удаляет оставшиеся строки crontab этих скриптов (иначе двойной запуск); новый перенос из cron — добавить имя скрипта в его параметр.
- **Не править `sources.sh` на месте, пока он работает:** `/bin/sh` дочитывает скрипт по смещению. Сначала `cp -p sources.sh sources.sh.tmp && mv -f sources.sh.tmp sources.sh` (новый inode, старый остаётся у процесса).

## `check_mytasks.sh`: стартовая настройка и проверка

- Один скрипт и для новой машины, и для регулярной проверки. Порядок: семейство ОС по `/etc/os-release` (`ID`, затем `ID_LIKE`; `detect_family`: `arch`, `debian`, `redhat` (Fedora Atomic — `rpm-ostree` по `/run/ostree-booted`), `suse`, `alpine`, `void`, `gentoo`, `solus`, `nixos` с менеджером пакетов `PKG_MGR`; нераспознанная ОС — `unknown` и предупреждение `OS_NOTE`, без systemd (`has_systemd`: `systemctl` и `/run/systemd/system`) юниты не создаются) → самоустановка в автозагрузку (user-юнит `check-mytasks.service`, `--no-create --notify` при входе в сеанс) → `conf/check_mytasks.conf` с `MYTASKS_DIR` = каталог запуска (при расхождении — предупреждение и правка до юнитов) → при первом запуске мастер всех отсутствующих конфигов → зависимости → задания → таблица. Таблица (`--status`) выводится всегда.
- Переносимость: шебанги только `#!/usr/bin/env bash` / `#!/usr/bin/env python3` (кроме `cloud_backup_qnap.sh` с Entware `#!/opt/bin/bash` и POSIX `#!/bin/sh`), в юнитах — `/usr/bin/env КОМАНДА` вместо `/usr/bin/КОМАНДА` (в NixOS нет `/bin/bash`, `/usr/bin/python3`, `/usr/bin/sleep`). GNU-утилиты (`find -printf`, `stat -c` и т.п.) проверяются зависимостями `gnu:find`/`gnu:stat` — в busybox (Alpine) их нет.
- Обязательный первый шаг — полное обновление системы (`system_update` → `__root-update` → `root_update`, команда по семейству в `detect_family`: `UPDATE_MGR`/`UPDATE_MODE`/`UPDATE_DESC`; Garuda — `garuda-update --noconfirm`, отключается `GARUDA_UPDATE="no"`). При сбое `UPDATE_OK=0`: пакеты не ставятся (частичное обновление), остальное проверяется; перезагрузка — `REBOOT_FLAG` или нет `KERNEL_MODULES_DIR/$(uname -r)`. Новое семейство добавлять и в `root_update`. Тесты подменяют `garuda-update`, `emaint`, `nixos-rebuild`, `transactional-update` и все менеджеры пакетов; реальный `garuda-update` в тестах вызываться не должен (заглушка первой в `PATH`).
- Жёстких путей в репозитории нет: шаблоны `systemd/*.{service,timer}` (системные), `systemd/user/` (пользовательские), `systemd/autostart/` (XDG) и примеры конфигов используют плейсхолдеры `@MYTASKS_DIR@` и `@HOME@`; их подставляет `check_mytasks.sh` (`subst`). Новые юниты добавлять шаблоном с плейсхолдером и записью в `JOBS`, не копировать вручную в `/etc` или `~/.config`. Установленный файл сравнивается с отрисованным шаблоном (без `cmp`: `same_file` в bash) — расхождение = «отличается», предлагается обновление.
- `JOBS` — `вид|имя|параметр|условие|описание` (виды `user-unit`, `system-unit`, `user-ext`, `system-ext`, `no-cron` (строк crontab с перечисленными скриптами быть не должно, исправление — удалить), `link`, `autostart`, `conf`, `venv`, `db`, `root-file` (`root-file|ИМЯ|ИСТОЧНИКИ:КАТАЛОГ:РЕЖИМ|условие|описание`: ИМЯ — имя файла назначения; ИСТОЧНИКИ — через запятую относительно mytasks, берётся первый существующий обычный файл внутри каталога скрипта, `*.example` — с подстановкой; КАТАЛОГ `lib` = `ROOT_LIB_DIR` (`/usr/local/lib/mytasks`), `conf` = `ROOT_CONF_DIR` (`/etc/mytasks`), в конфиг дописывается `MYTASKS_DIR`; РЕЖИМ `0755`/`0644`; владелец `root:root`; статусы «есть» / «нет» (копии нет) / «отличается» (содержимое или права не совпадают, либо на месте не обычный файл) — установка и обновление через `__root-install-file` с подтверждением), `linger` — `loginctl enable-linger` текущего пользователя, чтобы user-службы (`beufm-recorder.service`) работали с загрузки без входа в сеанс: сначала без прав (polkit), при отказе `__root-linger`; `health` — служба действительно работает: имя — user-служба без `.service`, параметр `МАСКА_ЛОГА:МИНУТЫ`, последняя запись самого свежего лога в `LOG_DIR` не старше МИНУТ и без ERROR в последних 200 строках, исправление — `systemctl --user restart` (задание `beufm-recorder`, 20 мин); условия `path:`, `cmd:`, `fs:ТОЧКА=ТИП`, `family:`), `DEPS` — `команда|пакеты|условие|описание`, пакеты — `имя;семейство=имя;…` (`-` — нет в репозиториях; `py:МОДУЛЬ` — системный Python, `opt` — необязательная). Новое семейство добавлять в `detect_family`, `root_pkg` и при отличии имён — в поле пакетов `DEPS`. Первые две строки (`check-mytasks.service`, `conf/check_mytasks.conf`) добавляет `apply_defaults`, их в `JOBS` не дублировать.
- Мастер конфигов (`parse_example`/`write_conf`): описание — комментарии над переменной, значение по умолчанию — из примера с подстановкой; неизменённые строки копируются из примера как есть (иначе `quote_value` экранирует `${HOME}`), массивы — по элементу на строку, файлы без переменных (`sources.conf`, JSON) — редактированием текста. `cloud_backup_qnap.conf` мастер не предлагает (`CONF_WIZARD_SKIP`).
- Вопросы — `ui_yesno`/`ui_input`/`ui_text`/`ui_choice`: сначала `zenity` (у kdialog `--cancel-label`/третья кнопка работают только в `--yesnocancel`, проверено скриншотами 2026-10-23), затем `kdialog`, без графики — терминал (stdin, `--ask`), без терминала — только предупреждения; `--yes` — всё обязательное без вопросов. «Отмена» — только текущее окно (конфиг не создаётся, поле — по умолчанию); «Стоп» (zenity `--extra-button`, kdialog `--yesnocancel` и пункт списка, в терминале «стоп») возвращает `STOP_RC` и через `request_stop` прерывает весь процесс: больше ничего не спрашивается и не меняется, печатается итоговая таблица. Значения, определимые на машине, подставляет `smart_default` (`OS_FAMILY`, `CUDA_ARCH`, `BUILD_JOBS`). Ответ «нет» запоминается на запуск (`HANDLED`, `SKIPPED_CONFS`): каждое задание обрабатывается за запуск один раз. Root-шаги — повторный запуск себя через `sudo -A`/`pkexec`/`sudo` с `__root-install-units`, `__root-install-file`, `__root-enable`, `__root-linger`, `__root-pkg`, `__root-update` (логи не пишут). Пользовательские сервисы входа в сеанс только `enable` (иначе `systemctl --user enable --now` ждёт oneshot с `sleep 60`), таймеры — `enable --now`.
- Схема привилегий: root-шаги (`__root-*`) разбираются в блоке ARGS до `load_user_conf` — под root пользовательский конфиг не выполняется (не под root, в тестах с `SUDO_CMD=""`, — из конфига, как у основного запуска). Аргументы проверяются: пакеты — только имена из `DEPS` (`dep_known_package`); юниты `__root-install-units` — `system-unit`, `__root-enable` — `system-unit`/`system-ext` из `JOBS`; файлы `__root-install-file` — только имена `root-file` из `JOBS`; linger — только для вызвавшего пользователя (`SUDO_USER`/`PKEXEC_UID`); `MYTASKS_DIR` = каталог скрипта. Каталоги назначения (`valid_dest_dir`) — абсолютные, без `.`, `..`, `//` и симлинков; под root каждый существующий компонент принадлежит root и не доступен на запись группе и остальным. Исходники (`valid_source`) — обычные файлы внутри каталога скрипта без симлинков. Плейсхолдеры `@ROOT_LIB_DIR@` и `@ROOT_CONF_DIR@` подставляет `subst` (как `@MYTASKS_DIR@` и `@HOME@`); в юнитах (`systemd/system-monitor.service`) — `ExecStart` root-копии. Осознанный компромисс: сам установщик `check_mytasks.sh` запускается от root из домашнего каталога (как `sudo make install`); граница — проверка аргументов выше, а не доверие к файлу.
- Вид `db` (`db|ИМЯ|команда|условие|описание`) — база SQLite: проверка — `<команда> --dry-run`; строка `[dry-run] будет:` значит «база отсутствует или устарела» (ВНИМАНИЕ), иначе OK со «схема vN». Исправление — запуск `<команда>` от пользователя, без root; нет исполняемого файла — ВНИМАНИЕ, а при исправлении «не создана: нет …». Владельцы (`system_monitor.sh --migrate-db`, `music_downloader.py --migrate-db`, `utility_bills.sh --migrate-db`) на актуальной базе обязаны печатать `[dry-run] схема БД уже vN …` без «будет:».
- В агентской песочнице запускать только `--status` или `--dry-run --no-gui`: без `--no-gui` при наличии `DISPLAY` откроются окна на экране пользователя. Тесты `tests/check_mytasks.bats` копируют скрипт и шаблоны во временный каталог, задают временный `HOME`, конфиг с `SUDO_CMD=""`, `OS_RELEASE_FILE`, каталогами юнитов в `TMP_DIR` и подменяют `systemctl`, `crontab`, `apt-get`, `pacman`, `dnf`, `notify-send`.

## `system_monitor.sh` и systemd

- `system_monitor.sh` кроме дисков опрашивает CPU (`sensors -j`, загрузка из `/proc/stat`, `/proc/loadavg`) и каждую GPU через `nvidia-smi`. `sensors` и `nvidia-smi` необязательны: при их отсутствии нет температуры CPU или раздела GPU, но запуск не завершается ошибкой. Работа проверена на Ryzen 7 5800X и RTX 3060 Ti.
- `shellcheck -o all` должен оставаться без замечаний. Вложенные вызовы `$(sql_escape ...)`/`$(html_escape ...)` внутри больших строк сначала выносить в `local`-переменные. Сценарии отсутствующих зависимостей тестировать с полностью изолированным `PATH` через `iso_path_without()` в Bats, а не только `PATH="$STUB_DIR:$PATH"`, иначе доступны реальные `sensors`/`nvidia-smi` машины.
- Скрипт работает от root, поэтому созданные им файлы (БД, `logs/system_monitor-*.jsonl`, `system_reports/system_monitor-*.html`, `latest.html`) отдаются владельцу из `FILE_OWNER` (`пользователь` или `пользователь:группа`; пусто/не задано = владелец и группа каталога скрипта; значение по умолчанию задаётся до конфига). `fix_owner` не от root ничего не делает, при уже нужном владельце `chown` не вызывает, использует `chown -h` (симлинки не разыменовываются), ошибка — только WARN; каталоги не трогает. Вызывается после `init_db`, при генерации отчёта и в `cleanup_logs`; при каждом запуске под root `fix_existing_owner` чинит и прежние файлы по маскам скрипта (чужие файлы не трогает). `--dry-run` печатает `[dry-run] будет: сменить владельца на …: N файлов`. Для тестов EUID подменяется `SYSTEM_MONITOR_EUID`. Юнит остаётся под root. Недостающие таблицы создаются только при создании новой базы (`db_create_sql`); существующая v1-база с отсутствующей таблицей не досоздаётся.
- **Схема БД меняется только миграцией:** версия — `PRAGMA user_version`, `DB_LATEST=1`. Новая база создаётся сразу в текущей схеме (`db_create_sql`). База со схемой старше v1 не поддерживается: `init_db` завершается ошибкой (код `db_version_unsupported`) без изменений, `--dry-run` предупреждает. Следующая смена схемы — DDL в функциях `ddl_<таблица>` и миграция v2 с пересборкой таблиц (образец миграции 1 — в истории git до её удаления в ноябре 2026); `ALTER TABLE` вручную не использовать.
- Ключ `--migrate-db` только создаёт базу или приводит схему к текущей, без опроса (с `-n` — план; несовместим с `--report`); `check_mytasks.sh` вызывает его видом `db`.
- Расписание — `systemd/system-monitor.{service,timer}`, устанавливаемые `check_mytasks.sh` в `/etc/systemd/system`; cron для него не использовать. Служба запускает root-копию `ExecStart=@ROOT_LIB_DIR@/system_monitor.sh --config @ROOT_CONF_DIR@/system_monitor.conf` (`/usr/local/lib/mytasks/system_monitor.sh`, задание `root-file`; настройки — копия `/etc/mytasks/system_monitor.conf` из `conf/system_monitor.conf`, без него — из примера). Root-копия читает только этот доверенный конфиг (обычный файл, владелец root, без записи для группы и остальных; иначе код 2); в нём `MYTASKS_DIR` обязателен. Изменения скрипта и `conf/system_monitor.conf` действуют на таймере только после «обновить» в `check_mytasks.sh`. Песочница: `NoNewPrivileges`, `PrivateTmp`, `ProtectSystem=strict`, `ProtectHome=read-only`, `ReadWritePaths=-@MYTASKS_DIR@/state -@MYTASKS_DIR@/logs -@MYTASKS_DIR@/system_reports` (`-` — нет каталога, не сбой), без сети (`RestrictAddressFamilies=AF_UNIX AF_NETLINK`), `MemoryDenyWriteExecute`; `PrivateDevices`, `DeviceAllow` и `CapabilityBoundingSet` не заданы — нужны диски, NVIDIA и smartctl. Другой путь `DB_FILE`/`REPORT_DIR` требует правки `ReadWritePaths` в юните. Под root скрипт отказывает при симлинках в путях каталогов данных и в файлах БД; лог создаётся эксклюзивно (noclobber), `latest.html` пишется через `mktemp` рядом и `mv`. Ключ `-c/--config ФАЙЛ` задаёт конфиг явно (разбирается до загрузки конфига). `Persistent=true` выполняет один пропущенный интервал при загрузке без двойного запуска, возможного с `@reboot`. В service задано `SuccessExitStatus=1`, потому что код `1` означает найденное критическое состояние, а не сбой unit.
- Из агентской песочницы `systemctl` не видит system D-Bus; для установки и проверки использовать `pkexec` либо запуск вне песочницы.


## `llamactl.sh` и `llamactl_tray.py`

- Управляют локальным llama.cpp (роутер `llama-server.service` на `:8080` с пресетами `/etc/llama.cpp/models.ini`, FIM `llama-fim.service` на `:8012`, модели `/var/lib/llama.cpp/models`) независимо от Zed/VS Code. Установлены ссылками `~/.local/bin/llamactl` и `~/.local/bin/llamactl-tray` (цели — `llamactl/llamactl.sh` и `llamactl/llamactl_tray.py`); трей в автозапуске `~/.config/autostart/llamactl-tray.desktop`. Для любых действий с llama.cpp агентам использовать `llamactl` (сначала `-n`), а не ручные `curl`/`systemctl`.
- Root-шаги — только через `sudo -A` root-хелпера `llamactl-root` (`llamactl/llamactl-root.sh`; путь — `ROOT_HELPER` в `conf/llamactl.conf`; `check_mytasks.sh` ставит его заданием `llamactl-root` (`root-file`) копией root:root 0755 в `/usr/local/lib/mytasks/llamactl-root`): команды `install-preset`, `restore-preset`, `swap-install` (по одному запросу пароля на действие; эти вызовы не пишут логи, чтобы в `logs/` не появлялись root-файлы). Пути — зашитые или из `/etc/mytasks/llamactl-root.conf` (владелец root, не выполняется, разбирается как `КЛЮЧ="значение"`); файлы пользователя читаются с его правами (`setpriv`); из сборки копируются только `bin/` и `lib/`, ничего не исполняется. Хелпера нет или он устарел — `llamactl` откажет в root-шаге с подсказкой запустить `check_mytasks.sh`.
- `add` без sha256 от Hugging Face отказывает; обход — `--no-verify` (скачивание без проверки). Размер файла сверяется, если Hugging Face его вернул. Правило sudoers `NOPASSWD` для сервисов классификатор Claude Code блокирует как выдачу прав — не предлагать.
- Каждая запись `models.ini` строит новую версию из **текущего** файла и устанавливает её между `preset_lock`/`preset_unlock` (`flock` на `PRESET_LOCK_FILE`, по умолчанию `${XDG_RUNTIME_DIR}/llamactl-models-ini.lock`): `preset_set_key`, `preset_apply_edit`, `add_apply_preset`, `remove_apply_preset`. Новый писатель `models.ini` добавлять только так; не строить файл заранее и не держать блокировку во время загрузки или редактора. `add` берёт её после скачивания, `edit` не применяет правку, если `sha256` файла изменился с открытия редактора. Обёртку вида `with_lock "$@"` не использовать: shellcheck `-o all` считает переданные функции невызываемыми (SC2329). Тесты: «add: правка models.ini во время загрузки не затирается», параллельные `preset set`, конфликт `preset edit`.
- Пресеты применяются без перезапуска роутера: `GET /models?reload=1`; при неудаче — `systemctl restart`, затем откат из `models.ini.bak-*`. `update` без `--ref` ставит последний релизный тег `bNNNN` (`LLAMA_REF="latest-tag"` в конфиге; `--ref ТЕГ|SHA` — явный тег или полный SHA коммита), сборку, `--version` и `ldd` делает от пользователя; root-хелпер `swap-install` ставит `bin/` и `lib/` в `/opt/llama.cpp.new`, меняет местами с `/opt/llama.cpp` (прежняя — `/opt/llama.cpp.prev`) и откатывается, если сервисы не ответили за `HEALTH_TIMEOUT_SECS` (90 с).
- jq-программы получают значения через окружение (`env.X`), а не `--arg`/`$x`: CI-проверка переменных без фигурных скобок не отличает jq-переменные от shell. Литерал `$ORIGIN` для RPATH собирается в `RPATH_LIT` по той же причине.
- Короткий `-n` означает dry-run только до имени команды (у `logs` свой `-n N`); `--dry-run`/`--json` допустимы в любом месте. `status`/`models` не пишут JSONL-логи — их каждые 5 с вызывает трей.
- Статус — единственный источник `llamactl_status.py` (stdlib: HTTP к роутеру/FIM, `/proc`, `statvfs`, NVML через ctypes с откатом на `nvidia-smi`, один `systemctl is-active`); `llamactl.sh status` вызывает его и только форматирует вывод, трей импортирует его по пути (`spec_from_file_location`) и опрашивает в фоновом потоке (сигнал Qt). Формат JSON менять синхронно в модуле, `cmd_status` и трее; не возвращать сбор статуса в bash (было 61–73 процесса и ~160 мс CPU на вызов, стало ~20 мс CPU, замер 2026-10-23).
- Трей: шебанг `/usr/bin/env python3` (NixOS), при отсутствии PyQt6 у найденного `python3` (venv) — `os.execv` системного `/usr/bin/python3`. PyQt6 импортируется только в графическом режиме, поэтому `--print-menu [--status-file]` проверяется в `tests/llamactl.bats` без дисплея; тесты статуса поднимают локальный `python3 -m http.server` вместо роутера (`start_router`) и задают `LLAMACTL_NO_NVML=1`, чтобы не читать реальную GPU. Ruff: `music_downloader/venv/bin/ruff check --line-length 130 llamactl/llamactl_tray.py llamactl/llamactl_status.py`.
- Тесты `tests/llamactl.bats` подменяют `curl` (роутер/FIM/Hugging Face), `systemctl`, `nvidia-smi`, `journalctl`, `git`, `cmake`; пресет и модели — во временном каталоге, `SUDO_CMD=""`. Сторонний `llama-server` в тесте `kill-foreign` — копия `sleep` с этим именем.
- `llama-vscode`: встроенные env расширения поднимают свои `llama serve -hf …` (в т.ч. gpt-oss с `-c 0 -np 2`) и падают по VRAM; в настройках VS Code `llama-vscode.env_start_last_used = false`, использовать только env «Локальный llama.cpp». `llamactl doctor` показывает такие процессы и кеши `~/.cache/huggingface`, `llamactl kill-foreign` их завершает.

## `music_downloader`: конфигурация и поведение

- Обязательный непустой `download_paths` находится в корне JSON рядом с `sites` и общий для всех мостов: каждый трек сохраняется во все перечисленные каталоги. Внутрисайтовых настроек каталогов нет. Синхронно поддерживать структуру рабочего JSON, `.json.example` и README, не заменяя реальные пути и лимиты примерными.
- Скачивание — сквозной round-robin по мостам (`fill_queue`/`read_category` в `run`): по одному треку от каждого моста за круг; очередь моста пополняется его следующей категорией, только когда опустела (не заранее — ссылки категорий с метками времени протухают), и другие мосты при этом не ждут. Прежний обход «уровнями категорий» заставлял вторые категории Sefon/LMusic ждать, пока Beu FM выкачает сотни песен журнала эфира. Тест — `test_run_round_robin_refills_each_site_without_waiting_for_big_queue`.
- Метрики запуска (`report_run` в конце `run`, в `finally` — пишутся и при остановке кодом `2`): строки лога `Итог <мост>`, `Итог поиска <источник>`, `Место: <папка>` (WARNING при остатке < 50 треков), `Итог запуска` и строка `bari: …` для совместимости; те же данные — запись в таблицу `runs` БД (JSON-колонки `sites`, `sources`, `destinations`). Драйверы кладут счётчики в `track["_search_stats"]` (общий словарь запуска; `find_audio` ведёт `queries/candidates/exact/relaxed/chosen/errors/seconds`, недостающие ключи считаются нулём). Новую метрику добавлять в `site_data["stats"]`/`report_run` и тест `test_run_writes_metrics_to_log_and_runs_table`.
- Корневые `download_max_seconds` (600, общий дедлайн трека) и `download_max_mb` (100, лимит одного файла сверх остатка папки) — превышение дает ошибку одного трека, запуск продолжается. Адреса скачивания только `http`/`https`; драйверы только `.py` внутри `drivers/` после `realpath`; `.part` открывается с `O_NOFOLLOW`; имена файлов с префиксом `_` для зарезервированных имён Windows (подробности — `music_downloader/README.md`, «Безопасность»).
- TLS не ослаблять: HTTPS идёт через штатный `requests.adapters.HTTPAdapter()` (`scraper.mount("https://", HTTPAdapter())` в `run`): проверка сертификата и имени хоста, уровень OpenSSL по умолчанию. Прежний `SSLAdapter` с `DEFAULT@SECLEVEL=1` на все `https://` снят 2026-11-12: рукопожатие со всеми 25 хостами драйверов (сайты, `search_sources`, CDN `cdn1–4.sefon.pro`, `storage.xpleer.com`, `dl3s4.muzofond.fm`, `cdn5.drivemusic.me`, `ru.hitmoz.org`, `prod-1.storage.jamendo.com`, `stream.beufm.kz`) проходит на SECLEVEL=2. Не оставлять HTTPS штатному `CipherSuiteAdapter` cloudscraper: он задаёт единственную кривую `prime256v1`, и `cdn2/cdn3.sefon.pro` отвечают `SSLV3_ALERT_HANDSHAKE_FAILURE` (ночь 2026-11-12, когда адаптер был снят без замены). Если новый хост падает с `dh key too small`/`ca md too weak`, ослаблять только для него (`scraper.mount("https://<хост>/", …)`) с причиной здесь; тест — проверка `scraper.mount` в `test_run_uses_global_destinations_for_all_sites`.
- `max_size_mb` ограничивает весь каталог с подкаталогами, по умолчанию 1024 МиБ; проверка в байтах выполняется при старте и перед каждым сохранением. `save_response` проверяет каждый блок потока, в том числе без `Content-Length`, и учитывает копии в дочерних целевых каталогах. При переполнении `DownloadLimitExceeded` удаляет `.part`, завершает процесс с кодом `2`, не записывает незавершённый трек в БД и не запускает сортировщик; уже скачанное не удаляется. Контроль рассчитан на один процесс, для сторонних параллельных записей нужны квоты файловой системы. Отсутствующий, пустой или неверного типа глобальный список, отсутствующие каталоги и уже заполненные каталоги также дают код `2`.
- Дедупликация БД (`downloads`): `artist/title` — служебные нормализованные ключи, а исходные строки драйвера хранятся в `original_artist/original_title` и используются для отчётов. `normalize_db_text` = NFKC + `casefold` + только `str.isalnum()` (все разделители, пробелы и пунктуация отброшены), поэтому «Вася & Петя» == «Вася +Петя» == «ВасяПетя»; слова не удаляются — «Song (Remix)» != «Song». Ключ проверяется по ID `<site>_<track-id>` и по паре `artist/title` (уникальный индекс). Плюс дедупликация по содержимому: `save_response` возвращает `(bytes, paths, sha256_hex)`, движок сверяет хеш с колонкой `filehash`; при совпадении только что записанные копии удаляются с диска, а строка пишется с `filehash = NULL` (`INSERT OR IGNORE`) — ID не качается повторно и не нарушается частичный UNIQUE. Хеш проверяется после загрузки — экономит место, не трафик. Индексы: `UNIQUE(artist,title)` и **частичный** `UNIQUE(filehash) WHERE filehash IS NOT NULL`. При открытии БД строки перенормализуются, дубликаты `artist/title` и не-NULL `filehash` схлопываются к самой свежей. Старые исходные поля заполняются доступными до нормализации значениями `artist/title`; уже потерянные прежней версией регистр и пунктуация невосстановимы. Схема БД меняется только миграцией: версия — `PRAGMA user_version`, новая миграция — следующий номер в `DB_MIGRATIONS` (`DB_LATEST` считается по нему), DDL таблиц и индексов — в одном месте (`DB_SCHEMA`, `table_ddl`); таблицы не править `ALTER` вручную. `_rebuild_table` приводит таблицу к **текущему** `DB_SCHEMA`, поэтому изменение схемы = правка `DB_SCHEMA` + новая миграция через `_rebuild_table`, не `ALTER TABLE ADD COLUMN` (на старой базе колонку уже создаст миграция 1). `migrate_database` выполняется в начале `_create_table`, ДО перенормализации и дедупа: новая база сразу получает `DB_LATEST`; существующая — резервную копию (`conn.backup()` в `<база>.bak-v<версия>-<ГГГГММДД-ЧЧММСС>`) и миграцию в транзакции. Миграция 1 пересобирает `downloads` и `runs` в схему кода (порядок колонок, недостающие — NULL, лишние отбрасываются); индексы при пересборке воссоздаются только те, что были в старой таблице, остальные (UNIQUE на ещё не дедуплицированных данных) создаёт обычная последовательность. `music_downloader.py --migrate-db [--dry-run]` — только миграции (без перенормализации и дедупа), dry-run печатает план `[dry-run] будет: …`. Порядок в `_create_table` важен: оба индекса снимаются ДО перенормализующего `UPDATE` и дедупа и создаются заново ПОСЛЕ — при более широком ключе `UPDATE` иначе нарушит ещё живой UNIQUE. Менять `normalize_db_text` только с бэкапом рабочей `music_downloader.db` (миграция удаляет схлопнувшиеся строки). Разовый backfill `filehash` по уже лежащим на диске файлам (`_cloud/` + разложенная `/mnt/copy/Music/<папка>/`) — `state/music_downloader_hash_cleanup.py` (dry-run без флага, `--apply` с бэкапом и JSON-отчётом); при штатной работе строки с `filehash = NULL` (файл не найден) не досчитываются.
- Очистка ID3 (`clean_mp3_tags` в `save_response`, нужен `mutagen`): в тегах остаются только данные о песне. Из полей песни вырезаются ссылки (со скобками или подводкой, начинающейся с глагола «скачано с…» — одиночные «by»/«on» не трогать), строки текста песни со ссылкой удаляются (переводы строк `\r\n` сохранять, иначе очистка неидемпотентна); `TIT2`/`TPE1` целиком не удаляются; TLD `by` и прочие похожие на слова зоны не распознаются («Prod.by»), почта не ссылка; `TCOP`/`TPUB`/`TXXX` со ссылкой, URL-кадры `W***`, `TOWN`/`TRSN`/`TRSO`, TXXX `comment`/`description`/`notes` уходят в комментарий; технические кадры (`TENC`, `TSSE`, `TLEN`, `PRIV`, `GEOB`, iTunes-`COMM`, технические TXXX ffmpeg/iTunes/рипперов) удаляются, ссылки из них — в комментарий. **TXXX целиком не переносить**: в библиотеке это в основном MusicBrainz/ReplayGain/ISRC/LABEL (замер 2026-10-21, ~12 TXXX на файл). Комментарий один, оптимизирован `optimize_comment` (короткие ссылки без схемы/`www`, без повторов, без hex iTunes и повторов названия/исполнителя/альбома). Очистка на копии `.part.tags`, сбой mutagen — предупреждение и файл как есть; размер и `filehash` — от итогового файла. Уже лежащие файлы библиотеки движок не трогает.

### Контракт драйверов, Shazam и MyChords

- Драйвер реализует `get_tracks(session, base_url, category)`. Необязательный `resolve_track(session, track)` движок вызывает только перед скачиванием нового трека, после проверки БД и общей очереди; результат — словарь `download_url/referer/src` либо `None`. При `None` или исключении трек пропускается без записи в БД, а пара «исполнитель—название» удаляется из `queued_tracks`.
- Драйверы загружаются через `spec_from_file_location`; каталог загрузчика отсутствует в `sys.path`, поэтому соседние драйверы подключать по пути, как `_load_driver` в Shazam, а не через `from drivers import`.
- Настройки драйвера (тайм-ауты, User-Agent, паузы, расписания повторов, лимиты, тайм-ауты `yt-dlp`) — словарь `SETTINGS` на уровне модуля драйвера со значениями по умолчанию; код читает их из `SETTINGS[...]` в момент вызова. Движок накладывает значения из блока `drivers.<имя файла без .py>` файла `music_downloader.json` через `apply_driver_settings` (`drivers/music_downloader_driver_settings.py`; неизвестный ключ, неверный тип и отрицательное число — warning и значение по умолчанию); источникам поиска настройки передаются в `track["_driver_settings"]` и применяются в `_load_driver` при загрузке. Новые параметры добавлять в `SETTINGS` и в блок `drivers` файла `music_downloader.json.example` (тест сверяет их); регулярки, селекторы и URL-шаблоны в `SETTINGS` не выносить.
- `shazam_com`: чарт `/ru-ru/charts/top-200/world` запрашивать с проверенными Firefox-заголовками `SETTINGS["chart_headers"]` — Chrome-профиль и `curl` без заголовков возвращали 405/204/чужую страницу. Shazam (Next.js App Router за Fastly) периодически отдаёт по адресу чарта HTTP 200 со страницей чужой песни (иной canonical, ~1.8 МБ вместо ~3.7 МБ), дефект держится до истечения TTL узла и виден не со всех маршрутов; полная HTML-страница и RSC-поток того же адреса ломаются независимо (наблюдались оба сочетания, и «оба сразу»). Поэтому `get_tracks` на каждой попытке пробует **два источника**: `parse_chart` (HTML: canonical + карточки `[data-test-id="songItem"]` с восстановлением SSR-вставок `$RS(...)`, ранги 1…200, 200 уникальных `adam_<id>`), затем при неудаче `parse_flight_chart` (RSC: заголовок `RSC: 1`, ответ `text/x-component`; те же данные регуляркой по `self.__next_f` — `"trackName"/"artistName"/…/song/<id>/`; ранг = порядок карточек, совпадает с DOM; те же ключи `adam_<id>`). Попытки — по `SETTINGS["retry_delays_seconds"]` (`15, 45, 90` с) с `Connection: close`. **Query-параметр-«антикэш» не добавлять** — отдельный ключ Fastly чаще указывает на битую копию. Легаси-JSON `cdn.shazam.com/shazam/v3/.../genre-global-chart-1` **не использовать** — он заморожен на данных начала 2024 г. `ERROR` пишется только после того, как оба источника промолчали на всех попытках, и означает временный сбой Shazam/CDN; на поломку разбора указывают `В карточке чарта…` / `Ожидался полный Top 200…` / `RSC-поток Shazam…` при живом чарте. RSC-ответ `text/x-component` приходит без charset — `requests` декодирует его как ISO-8859-1 (mojibake «Ã©», «Ð¢Ð°Ñ…», такие треки не находились в поиске), поэтому `get_tracks` ставит `response.encoding = "utf-8"`; не убирать. Аудио искать только через общий `search_sources` (точное совпадение `match_key`); превью Shazam/Apple не использовать.
- **Общие источники MP3 — один список `search_sources`** в корне `music_downloader.json` (`name`, `enabled`, `driver`, `base_url`, `search_path` с `{query}`); движок кладёт его в `track["_search_sources"]` перед `resolve_track`, без ключа — встроенный `DEFAULT_SOURCES` (Sefon → LMusic). ## Библиотека `/mnt/copy/Books`

- Библиотека находится вне Git. Не добавлять книги и сгенерированные отчёты из `state/` в репозиторий. Перед удалениями создавать локальный JSON-отчёт с путями, размерами и причинами.
- При дедупликации удалять только подтверждённые копии. Если одна книга есть в нескольких форматах, удалять TXT только при наличии полноценного `fb2`, `epub`, `pdf` или аналогичного варианта. Не включать в дедупликацию и граф исходные `.html`/`.htm` и каталоги ресурсов `*_files`, `*.files`, `* files`.
- RTF, DOC, DOCX и CHM преобразовывать в EPUB; исходник удалять только после проверки ZIP/CRC, `mimetype`, `META-INF/container.xml`, содержательных страниц и текста. Повреждённый CHM сначала проверять независимыми средствами (`ebook-convert`, chmlib, 7-Zip); физически неполный и невосстановимый файл удалять только с отчётом.
- Если нужен `sudo`, использовать наиболее подходящий для операционной системы графический askpass/аутентификатор с явным пользователем `esimych`; не запрашивать пароль в чате и не сохранять его.
- Отдельный граф библиотеки хранится в `state/books-graph/graphify-out/`. После изменения состава книг полностью пересобирать его через `state/build_books_graph.py`, проверяя итоговые счётчики, ошибки сканирования, оборванные связи и отсутствие временных `.part.epub`.
