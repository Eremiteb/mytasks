# Best practices

Правило границы: практика применяется, только если решает реальную проблему
здесь и сейчас. Простейшее рабочее решение важнее «правильной» архитектуры.
Правила проекта (`AI.md`, `AGENTS.md`, `CLAUDE.md` и т. п.) и пользователя важнее
этого навыка; ослабление защиты — только с явного согласия пользователя.

## Перед правкой
- Прочитай код, места вызова, конфиг и логи; не правь по догадке.
- Найди первопричину, а не симптом; не лечи следствие заплаткой.
- Бритва Оккама: если нужное поведение уже есть (событие в логе, проверка,
  настройка), используй его, а не добавляй второй механизм; дифф — минимально
  достаточный, чужой код не «улучшай» заодно.
- Перед удалением или переименованием найди все ссылки (`grep -r`, граф проекта).
- Перед правкой скрипта проверь связанные начальные, установочные и миграционные
  скрипты и после изменения синхронно обнови их.

## Код
- Ошибки явные: в bash `set -euo pipefail`, проверка кодов выхода; в Python
  конкретные исключения там, где их можно обработать, без голого `except: pass`
  и без `|| true` ради подавления. Сбой одной единицы работы (файла, письма,
  записи) не роняет весь запуск.
- Ресурсы освобождаются гарантированно: `with`/`try…finally`, `trap` в bash.
- Скрипты идемпотентны: повторный запуск безопасен (`mkdir -p`, `IF NOT EXISTS`,
  проверка перед действием). У скрипта, меняющего данные, есть `--dry-run`.
- Никакого хардкода путей, секретов, доменов, адресов: из env/конфига; корень
  проекта — по расположению файла. Настройки и константы — в конфигурации.
- Типизация и структуры: аннотации типов в Python, `dataclass`/типизированные
  объекты вместо словарей-«мешков».
- Валидация входа (аргументы CLI, конфиг) с понятными сообщениями; взаимоисключающие
  режимы CLI — взаимоисключающая группа.
- Таймаут на каждый сетевой вызов (`curl --max-time`, `timeout=` в Python).
- Запись файлов атомарная: временный файл (`tempfile`/`mktemp`) в том же каталоге
  и `rename`; без предсказуемых имён в общих каталогах.
- Функции с одной ответственностью, имена говорящие; комментарий объясняет
  «почему», а не «что».
- Мёртвый код, неиспользуемые опции и ветки совместимости удаляй, не оставляй
  «на всякий случай».
- Shell: кавычки и `${VAR}` вокруг переменных, `[[ ]]`, у каждого `case` ветка `*)`;
  ввод не подставляй в команды без экранирования. Скрипт проходит
  `shellcheck -o all` и `-S style` без отключений — исправлять реструктуризацией
  (SC2312: вынести подстановку в отдельную переменную).
- Тестируемость: сеть, процессы и время подменяемы; на новое поведение — тест.

## Конфигурация и инфраструктура
- Версии зафиксированы: образ по digest или точному тегу, зависимости по версии.
- Декларативно: состояние описано в файле, а не набрано руками на сервере.
- У сервиса есть healthcheck, лимиты памяти/CPU и ротация логов.
- Периодика — таймеры systemd (`.service` + `.timer`), не cron.
- Изменение применимо повторно и откатываемо; перезапуск не ломает состояние.
- Решения (модели, библиотеки, параметры) — под фактическое железо и версии
  машины, подтверждённые измерением, а не общими предположениями.

## Данные
- Перед необратимым (миграция, удаление, перезапись) — бэкап или снимок.
- Схема БД меняется версионной миграцией; применённые миграции не правь.
- Бэкап считается рабочим, только если восстановление проверено.
- Боевой запуск — только после успешного `--dry-run` с теми же аргументами и
  конфигом и подтверждения пользователя.

## Проверка
- Проверки кода (тесты, линтеры, `bash -n`, `shellcheck`, `py_compile`, `ruff`)
  выполняет CI репозитория; локально их не запускать. Нужной проверки нет в
  CI — добавить её в workflow. «Проверено» значит зелёный CI.
- Поведение на реальной системе проверять можно и нужно: `--dry-run`, запрос к
  сервису, статус контейнера, строка в логе, код выхода.
- Отчёт честный: что запущено, какой результат (с выводом), что не проверено и почему.
- Упало — не «починено», пока не понятна причина.

## Изменения
- Коммит атомарный: одна тема; в сообщении — «почему», не только «что».
- Документация (README, `.env.example`/шаблон конфига, скрипты в `scripts/`)
  обновляется в том же изменении; рабочий конфиг — без потери значений и секретов.
- Не коммить секреты, `.env`, дампы, артефакты сборки, кэши, `graphify-out/`.

## Эксплуатация
- Наблюдаемость: метрики, логи, алерты на то, что реально ломается.
- О близости к лимиту (память, диск, PID, квота, таймаут) сообщай сразу:
  какой лимит, значение, что теряется, варианты.
- Предупреждения не маскируй и не называй «штатными» без доказательства; чини в корне.
- Длительные операции — с видимым прогрессом (этап, процент, скорость, остаток).

## Анти-паттерны
- Абстракция «на вырост», слой без второго потребителя, конфиг-опция без пользователя.
- Код «на всякий случай» и ветки совместимости без живого потребителя.
- Копипаста конфигов вместо общего блока (`x-` якорь в compose, include).
- Отключение проверки (`# shellcheck disable`, `--no-verify`, `|| true`) вместо исправления причины.
- Ретраи и `sleep` вместо ожидания условия (healthcheck, `until`).
- Новая зависимость ради десяти строк стандартной библиотеки.
- Второй механизм для того, что уже есть.

Перед сдачей задачи пересмотри свой дифф по этому навыку и по чек-листу infosec;
осознанные компромиссы назови пользователю явно и с причиной.
